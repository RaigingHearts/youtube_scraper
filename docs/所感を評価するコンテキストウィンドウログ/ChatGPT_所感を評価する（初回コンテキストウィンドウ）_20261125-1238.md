## 実用を意識した初期バージョン

## 1. プログラム全体の構成

これは今後、例えば次のような機能を追加するときに有利です。

- コメント取得結果のCSV変換

## 2. 特に良いと思ったところ

### ① Rawデータを保存する設計

これは非常に良い判断だと思います。

`youtube_api_client.py` では、取得したレスポンスを次の3種類に分けて保持しています。

| データ | 保存内容 |
|--------|--------|
| 動画情報 | `video_info_raw` |
| チャンネル情報 | `channel_info_raw` |
| コメント情報 | `comment_threads_raw` |

そして、加工済みのコメント一覧などではなく、APIレスポンスをJSONとして保存する設計です。

この方式には大きな利点があります。

例えば、今後コメントの分析方法を変更したくなった場合でも、YouTubeに再アクセスすることなく、保存済みデータから再処理できます。

また、取得時点の動画情報・チャンネル情報も一緒に残るため、後からデータを検証する際にも役立ちます。

個人的には、このプログラムの設計で最も評価したい部分の一つです。

### ② APIキーの管理を独立させている

`settings_manager.py` では `cryptography` のFernetを利用してAPIキーを暗号化し、設定ファイルに保存しています。

APIキーをソースコードに直接記述せず、初回起動時に入力させる構成も適切です。

さらに、設定管理とTkinterの入力ダイアログを別モジュールに分けています。

ただし、暗号化については注意点があります。

現在は暗号化キーを `youtube_scraper-encryption_key.key` として、暗号化済み設定ファイルと同じ環境に保存しています。

つまり、両方のファイルを取得できる人はAPIキーを復号できます。

したがって、これは設定ファイルをそのまま読まれにくくするための保護としては有効ですが、強固な秘密情報保管機構とは異なります。

将来的にはWindowsの資格情報マネージャーなど、OS側の保管機能を利用する方法も考えられます。

### ③ GUIと取得処理を別スレッドにしている

`tk_async_tasks.py` を用意し、時間のかかるAPI通信を別スレッドで実行する構成も良いです。

コメントが数百件、数千件と増えても、取得中にウィンドウが固まりにくくなります。

また、進捗表示や取得件数表示も実装されており、単純なスクリプトではなく、ユーザーが操作するアプリケーションとして考えられています。

このあたりは実用性を意識した設計だと感じました。

## 3. 優先して修正したい問題

ここからは、実際のコードを読んで見つけた問題です。

### ① 返信コメントをすべて取得できない可能性がある

(最優先)

これは重要です。

`youtube_api_client.py` では、次のようにコメントを取得しています。

```python
request = service.commentThreads().list(
    part="snippet,replies",
    videoId=video_id,
    maxResults=100,
    pageToken=next_page_token,
    textFormat="plainText"
)
```

この方法でコメントスレッドと返信を取得できます。

しかし、YouTube Data APIの `commentThreads.list` が返す返信情報は、スレッドに属するすべての返信を網羅するとは限りません。

返信が多いスレッドでは、完全な返信一覧を取得するために、別途 `comments.list` を `parentId` 指定で呼び出してページングする必要があります。

つまり、現在のプログラムは「コメントをすべて取得する」としていますが、返信数の多い動画では実際のコメントを取りこぼす可能性があります。

これはプログラムの目的そのものに関わる問題です。

**改善案**

1. `commentThreads.list` でコメントスレッドを取得する。
2. 各スレッドのトップレベルコメントを保存する。
3. 返信が存在するスレッドについて `comments.list` を呼び出す。
4. `nextPageToken` がなくなるまで返信を取得する。
5. トップレベルコメントと返信を紐付けて保存する。

このようにすれば、返信コメントまで網羅する構造にできます。

### ② 取得件数の計算と進捗表示に問題がある

現在は、次のように取得件数を計算しています。

```python
for item in response.get("items", []):
    comments_fetched_count += 1
    if "replies" in item:
        comments_fetched_count += len(
            item["replies"].get("comments", [])
        )
```

この計算自体は、APIレスポンスに含まれているトップレベルコメントと返信を数えるものです。

しかし、先ほどの返信取得の問題があるため、実際の総コメント数とは一致しない可能性があります。

さらに、進捗表示の分母に利用している `pageInfo.totalResults` はコメントスレッド数を基準とするため、返信も加算した取得件数とは単位が一致しません。

例えば、次のような状態が発生し得ます。

| 項目 | 件数 |
|--------|--------|
| コメントスレッド | 100 |
| トップレベルコメント | 100 |
| 返信コメント | 400 |
| 実際のコメント数 | 500 |

この場合、進捗表示の分母は100、取得件数は500という関係になり得ます。

進捗バーの表示としては正確ではありません。

取得済みスレッド数と取得済みコメント数を別々に管理するのがよいと思います。

### ③ APIエラーが発生しても正常終了扱いになる場合がある

(最優先)

ここは少し気になりました。

`fetch_all_comments()` は、API通信に失敗した場合でも、基本的には次のような辞書を返します。

```python
{
    "video_info_raw_response": {},
    "channel_info_raw_response": {},
    "comment_threads_raw_responses": []
}
```

ところが、`main.py` 側では、

```python
if result_data:
```

という判定をしています。

Pythonでは、中身が空の辞書でない限り、辞書そのものは真として扱われます。

したがって、APIサービスの構築に失敗した場合でも、`result_data` が空ではないため、正常取得後の保存処理に進む可能性があります。

さらに、コメント取得途中でAPIエラーが発生した場合も、取得済みデータを返す設計になっています。

この場合も、取得が完了したかどうかを区別できません。

**改善案**

取得結果に成功・失敗・中断・部分取得を示すステータスを設けることをおすすめします。

例えば、

```python
{
    "success": False,
    "status": "partial",
    "video_info_raw_response": {},
    "channel_info_raw_response": {},
    "comment_threads_raw_responses": []
}
```

のような形式です。

こうすれば、GUI側で「正常完了」「一部取得」「取得失敗」を正確に表示できます。

### ④ Tkinterのスレッド処理に問題がある

`main.py` ではコメント取得処理を別スレッドで実行しています。

その一方で、確認ダイアログについては、

```python
def confirm_callback(message: str) -> bool:
    return tk_notifications.ask_yes_no(
        "確認", message, parent=self.master
    )
```

としています。

この関数は、バックグラウンドスレッドから呼び出されます。

つまり、Tkinterのダイアログをメインスレッド以外から直接操作していることになります。

Tkinterは基本的にメインスレッドからGUIを操作する必要があるため、環境やタイミングによって不具合が発生する可能性があります。

実は、これを解決するための仕組みは既に `tk_async_tasks.py` にあります。

```python
confirm_continuation_gui()
```

この関数は `after()` と `wait_variable()` を使って、メインスレッド側で確認ダイアログを表示する構造です。

せっかく用意されているので、`main.py` 側でもこちらを利用するのがよいでしょう。

同様に、API通信中のエラー通知などもGUIスレッド経由に統一したいところです。

## 4. その他の改善点

## 6. 今後の発展性

個人的には、このプログラムはコメントを取得するだけで終わらせるには惜しい構造だと思います。

Raw JSONを保存する方針を維持したまま、後処理を独立したモジュールとして追加すると、かなり発展性があります。

例えば次のような構成です。

## 将来的な拡張構成案

**YouTube Data API**

動画・チャンネル・コメントの取得

**Raw JSON保存**

取得時点のデータを保管

**データ整形**

コメント・返信の構造化

**データ分析**

投稿者・日時・頻出語など

**データ出力**

CSV・Excelなど

**検索・閲覧**

コメントの検索・抽出

このようにすれば、YouTubeからデータを取得する部分と、取得済みデータを活用する部分を切り離せます。

これは現在のモジュール構成とも相性がよいと思います。
