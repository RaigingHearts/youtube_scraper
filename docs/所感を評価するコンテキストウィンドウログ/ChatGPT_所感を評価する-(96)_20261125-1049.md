## 6. 11月24日夜：目的と費用対効果の再評価

ここが今回の最も重要な転換点です。

ユーザーから、次の問題提起がありました。

- 実機GUI受け入れテスト自動化の目標のためだけに、これだけの作業量を費やしている。
- テストの実行に関わる必要性は本当にあるのか。
- テスト準備と実施にかかるユーザー負担に見合っているのか。
- そもそも実機GUI受け入れテスト自体が必須なのか。
- 個人がバイブコーディングで実装しているプログラムに、そこまで厳密な検証が必要なのか。

これに対して、最終的に次の結論になりました。

**実機GUI受け入れテストとその自動化は、今回のプログラムでは必須要件ではない。**

理由は明確です。

1. 個人利用を目的としたプログラムであり、企業向け業務システムと同等の検証体制を要求する必要はない。
2. GUI自動テストを維持するための準備・実施・保守コストが大きい。
3. OCRの精度調整に時間をかけることが、プログラム本来の実装・改善を圧迫している。
4. GUIの基本動作は必要に応じて実際に使って手動確認できる。
5. 主要処理の単体テストや外部サービス連携確認など、より直接的な品質確認を優先すべきである。

ここで、内部テストまで不要と判断したわけではありません。

| 検証項目 | 今後の扱い |
|--------|--------|
| 構文・インポート確認 | 継続 |
| 主要処理の単体テスト | 継続 |
| 外部サービスとの連携確認 | 継続 |
| 必要に応じたGUI手動確認 | 継続 |
| 実機GUI受け入れテスト自動化 | 現時点では不要 |
| OCRによるGUI表示判定 | 現時点では不要 |
| 画像のピクセル単位の調整 | 終了 |

将来、GUI変更の頻度や手動確認の負担が増え、自動化の費用対効果が明確になった場合に限り、必要な範囲で再検討するという方針です。
