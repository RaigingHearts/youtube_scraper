## 共通インターフェースの確認結果

現行の設計書では、基盤の骨格はすでに定まっています。

- `main.py` がGUI要求キューを所有し、メインスレッドでポーリングする。
- `tk_async_tasks.py` が `GuiRequest` と `WorkerHandle`、ワーカー起動処理を担当する。
- ワーカーは `WorkerHandle` を第1引数として受け取り、結果・例外を格納する。
- ワーカーは同時に1つだけ動かし、終了後もGUI側の後処理が終わるまでハンドルを保持する。
- 進捗は最新値に集約し、通知はFIFO、確認要求は個別の `Event` で応答する。

この方向性自体に矛盾は見当たりません。ただし、現状の記述は属性名や役割の宣言が中心で、実装に必要なデータ形式・状態遷移までは確定していません。

### 1. `WorkerHandle` とワーカー起動

設計書間で整合している点は、次のとおりです。

| 項目 | 現時点の仕様 |
|--------|--------|
| `thread` | 実行スレッド |
| `gui_request_queue` | GUI要求の受け渡し先 |
| `cancel_event` | 協調的キャンセルの通知 |
| `done_event` | ワーカー終了の通知 |
| `result` | 正常終了時の戻り値 |
| `exception` | 例外終了時の例外 |
| 追加情報 | 最新進捗、Lock、進捗マーカー状態、保存方針、未回答確認要求 |

`run_task_in_thread()` は `WorkerHandle` を返し、ワーカー関数にはそのハンドルを第1引数として渡す設計です。

ここで、実装前に明文化したい点が3つあります。

- **スレッド開始失敗時の扱い：** `Thread.start()` が失敗した場合、呼び出し元へ例外を伝える仕様です。したがって、`main.py` は起動失敗時にボタン等のGUI状態を復旧させる必要があります。
- **完了判定とハンドル解放：** `done_event` が設定されただけでは解放しません。キューに残った要求、結果・例外、GUI側の完了処理まで回収してから解放します。
- **次のワーカーの起動条件：** ワーカーのスレッド終了だけでなく、前のワーカーのGUI側後処理も完了していることが条件です。

### 2. `GuiRequest` とキュー処理

現行仕様では `kind` が次の3種類です。

- `progress`：進捗更新
- `notification`：情報・警告・エラー通知
- `confirmation`：継続確認

通知はFIFO、進捗は最新値への集約、確認は要求ごとの `response_event` で応答するため、3種類の処理方式を分ける設計は合理的です。

一方、以下はまだ具体化が必要です。

1. `payload` の項目名・型・必須項目。
2. `confirmation` の回答値をどのタイミングで確定し、どのように未回答要求一覧から外すか。
3. 処理中にワーカーが終了した場合、残っている要求をどこまで処理してからハンドルを解放するか。
4. 進捗マーカーがキューに残ったままワーカーが終了した場合、そのマーカーをどう扱うか。
5. 1回最大50件の処理上限に達した場合も、次回ポーリングを必ず予約すること。

特に5番は重要です。キューが空になったときだけ次回ポーリングを予約する実装にすると、50件を超える要求が残った場合に処理が止まるおそれがあります。

また、現行の設計では `main.py` がキューを所有する一方、`WorkerHandle` にも `gui_request_queue` を保持します。これは「アプリケーション全体で共有するキューをハンドルから参照する」という構造にすれば整合します。ワーカーごとに別キューを作るのか、共有キューを使うのかは、実装前に明記したいところです。

### 3. 現行コードとの接続上の問題

現行 `main.py` の `_scrape_comments_task()` は、API取得・保存だけでなく、GUI更新・通知・GUI状態の変更まで行っています。

Stage 2の設計に従うなら、移行後は次のように責務を分離します。

| 処理 | 担当 |
|--------|--------|
| API通信 | ワーカー |
| JSONファイル保存 | ワーカー |
| 進捗情報の発行 | ワーカー |
| GUIへの通知要求 | ワーカー |
| ウィジェット更新 | メインスレッド |
| 通知ダイアログ表示 | メインスレッド |
| 保存先パス等のGUI状態更新 | メインスレッド |
| 完了・例外の回収 | メインスレッド |

この分離によって、ワーカーが `self.master` や各種ウィジェットに触れずに済みます。Stage 2の設計はこの点を明確に要求しており、Stage 1の基盤設計とも矛盾しません。

### 4. 追加で注意すべき競合

もう1点、通知のモーダル表示には注意が必要です。

Tkinterのモーダルダイアログは、表示中も内部的にイベント処理を継続します。そのため、ダイアログ表示中に次のポーリングが実行され、別の通知ダイアログを開いてしまう可能性があります。

設計書の「1件ずつ表示」「入れ子を避ける」を確実に守るには、単に通知をFIFOで取り出すだけでは不十分です。**通知ダイアログ表示中は次の通知表示を抑止し、閉じた後に次の通知を処理する仕組み**が必要です。終了待機中の通知保留とも連携させる必要があります。

## Stage 2・3の接続確認

ここでは、進捗・通知・継続確認が共通基盤にどう接続されるかを確認しました。大枠は一貫していますが、APIエラー通知の責務分担に、実装前に整理しておきたい点が見つかりました。

### 1. 進捗通知

Stage 2では、進捗をキューに毎回積むのではなく、`WorkerHandle` に最新値を保持して、キューには「進捗が更新された」というマーカーだけを登録します。

この方式なら、API取得が速く進捗更新が大量に発生しても、古い進捗要求がキューに大量蓄積するのを防げます。

ただし、次の競合対策は必須です。

- ワーカーが最新進捗を更新する処理
- マーカー登録済みフラグの確認・変更
- GUI側が最新進捗を取得する処理
- マーカー登録済みフラグを解除する処理

これらを同じ `Lock` の管理下で整合させる必要があります。設計書にはその方針が記載されているため、ここは実装時のテストで競合・取りこぼしがないことを重点的に確認する項目です。

### 2. 通知要求とAPIエラーの関係

現行の `youtube_api_client.py` は、APIエラー発生時に `tk_notifications` を直接呼び出しています。一方で、同じエラーの情報を `result_data["errors"]` にも記録しています。

Stage 3ではAPIクライアントからGUI依存を取り除き、エラー情報を返却する方針です。

ここで注意したいのは、**同じエラーを二重に通知しないこと**です。

例えば、APIクライアントがエラーを `result_data["errors"]` に記録し、ワーカー側でも通知要求をキューに登録し、さらに `main.py` が取得結果の総括通知を表示すると、同じエラーが複数回表示される可能性があります。

現時点では、次の役割分担が最も自然です。

- APIクライアント：エラー情報と取得状態を結果に記録する。GUI通知は行わない。
- ワーカー：必要な通知要求をGUIキューへ登録する。ただし、結果の総括通知と重複する通知は登録しない。
- メインスレッド：取得結果と保存結果を集約し、最終的な通知を表示する。

この整理なら、APIクライアントをGUIから独立させつつ、現行のエラー情報も維持できます。

### 3. APIクライアント内で確認できた通知箇所

現行コードでGUI通知を直接呼び出している箇所は、主に次の系統です。

| 発生箇所 | 現行の処理 |
|---|---|
| YouTubeサービス構築 | エラー通知後、取得処理を終了 |
| 動画情報取得 | エラーを記録・通知して終了 |
| チャンネル情報取得 | エラーを記録・通知して後続処理へ |
| 返信ページ取得 | エラーを記録・通知し、現在のスレッドページ処理を中断 |
| コメントスレッド取得 | エラーを記録・通知して取得ループを終了 |
| 動画が見つからない場合 | 警告を記録・通知して取得ループを終了 |

このうち、返信取得エラーなどは「取得済みデータを保存対象に残す」という説明も通知文に含んでいます。単純にダイアログ呼び出しだけを削除するのではなく、エラー記録・取得継続／中断の挙動・保存対象を維持しなければなりません。

また、サービス構築失敗では `get_youtube_service()` が `None` を返し、`fetch_all_comments()` が `service` エラーを `result_data` に記録して戻ります。この既存の返却経路を利用すれば、APIクライアント側に通知キューを持たせる必要はありません。

### 4. 継続確認のEvent方式

現行の継続確認は、APIクライアントからコールバックを呼び、旧 `tk_async_tasks.confirm_continuation_gui()` が `BooleanVar` と `wait_variable()` で回答を待つ方式です。

Stage 3ではこれを次の流れに置き換えます。

1. ワーカーが `confirmation` 要求をキューに登録する。
2. メインスレッドが要求を取り出し、確認ダイアログを表示する。
3. 回答値を要求に設定する。
4. `response_event` を設定する。
5. ワーカーはEventの設定を待ち、回答に応じて取得を続けるか中止する。

この変更によって、ワーカーはTkinterの変数やイベントループに触れずに済みます。

ただし、**回答値の確定とEvent設定を、終了処理による解除と競合させない仕組み**が必要です。設計書は「確定済み応答を上書きしない」としていますが、回答確定・未回答一覧からの除去・Event設定の一連の処理をどう排他制御するかは明記されていません。

ここはStage 4の終了処理と一体で設計する必要があります。

### 5. Stage 2・3で残る設計上の確認事項

現段階で、次の4点を未確定事項として整理します。

| 項目 | 確認・決定が必要なこと |
|---|---|

## 2. 発生し得る競合と対策

### A. 終了確認ダイアログを表示している間にAPI通信が終わる

これは今回の調査で最も重要な問題です。

例えば、次の順序が考えられます。

1. ワーカーがAPI通信を実行中。
2. ユーザーがウィンドウの閉じるボタンを押す。
3. 終了確認ダイアログが表示される。
4. その間にAPI通信が終了する。
5. ワーカーが通常処理としてJSON保存を開始する。
6. ユーザーが「いいえ」を選択する。

これでは「保存せず終了」を選んでも、既に保存が始まってしまいます。

**対策案：保存方針が確定するまでワーカーを保存開始地点で待機させる仕組みを設けます。**

具体的には、終了確認中であることを示す状態と、保存方針を確定させるための同期機構を設けます。

| ユーザーの選択 | ワーカーの動作 |
|--------|--------|
| はい | 保存方針を保存許可に確定してからキャンセルを通知 |
| いいえ | 保存禁止に確定してからキャンセルを通知 |
| キャンセル | 終了確認中の状態を解除し、通常処理へ復帰 |

これなら、API通信が終了してもワーカーは保存方針が確定するまで先へ進めません。

なお、終了要求より前に既に始まっていた保存処理は強制中断しません。これは現行設計の方針とも整合します。

### B. API通信中に終了要求が発生する

現行のYouTube APIクライアントは、以下のAPI通信を同期的な `.execute()` で実行しています。

- 動画情報取得
- チャンネル情報取得
- コメントスレッド取得
- 返信コメント取得

この通信を実行中に強制停止する仕組みはありません。

したがって、設計書の方針どおり、

- 通信開始前にキャンセルを確認する。
- 通信中は強制停止しない。
- 通信が戻ったら取得済みレスポンスを保持する。
- 次のAPI要求へ進む前にキャンセルを確認する。

という流れが適切です。

例えば、コメントスレッド取得中に終了要求が発生した場合、取得済みのページは保持し、次のページを要求せずに終了へ進みます。

ただし、API通信が長時間戻らない場合、終了もその間待機します。現在の設計ではタイムアウトを新設しない方針なので、これは既知の制約として残ります。

### C. 継続確認ダイアログと終了要求が競合する

Stage 3で設計した継続確認は、ワーカーが `threading.Event` を待ち、メインスレッドが回答を設定する方式です。

ここで終了要求が入った場合は、

1. 未回答の継続確認要求をFalseで解除する。
2. 対応するEventを必ず設定する。
3. 既に確定した回答は上書きしない。
4. 終了処理中は新しい継続確認ダイアログを表示しない。

という扱いが必要です。

また、ダイアログの表示中に終了要求が入るケースでは、ダイアログの回答と終了処理の回答が二重に確定しないよう、要求ごとの回答確定状態を管理する必要があります。

### D. 保存失敗・ワーカー例外

現行の `save_json_to_file()` は成功時に `True`、失敗時に `False` を返します。

保存対象は次の4種類です。

- 動画情報
- チャンネル情報
- コメントスレッド
- 返信コメント

Stage 4では、これらの保存結果をワーカー側で回収し、メインスレッドへ返す必要があります。

例えば4ファイル中1ファイルが失敗しても、残りの保存結果は保持します。保存失敗によってワーカーの終了処理やGUIの終了処理まで停止させてはいけません。

ワーカー自体が例外終了した場合も、例外を `WorkerHandle` から回収し、ログと必要な通知を処理してから終了する形が適切です。

## 3. 設計書に追加・明確化したい点

現行のStage 4設計は基本方針としては妥当ですが、次の項目は実装前に仕様を確定させたいです。

| 項目 | 現状 | 必要な整理 |
|--------|--------|--------|
| 保存開始前の同期 | 保存方針を確定してからキャンセルする方針のみ | 保存方針確定前に保存へ進めない仕組み |
| 状態管理 | running / confirming / waiting / complete | 終了確認中の状態と遷移条件 |
| 通知の保留 | 終了待機中は保留 | 重要通知の判定、集約、表示順 |
| 進捗要求 | GUIキューに登録 | 終了中は古い進捗を破棄してよい |
| 確認要求 | 未回答をFalseで解除 | 遅延回答との競合を防ぐ確定ルール |
| キャンセル状態 | `fetch_status="cancelled"` を再利用 | 継続拒否とアプリ終了によるキャンセルの区別 |
| ワーカー例外 | 回収する方針 | GUI状態の復旧と終了時の通知 |
| スレッド開始失敗 | 呼び出し元へ伝える方針 | ボタン状態などの復旧手順 |

### 特に `fetch_status="cancelled"` の扱い

現行コードでは、ユーザーが継続確認で「いいえ」を選んだ場合にも `cancelled` になります。

今後はアプリ終了によるキャンセルも同じ値を使うため、単に `cancelled` だけでは中断理由を判別できません。

私の推奨は、既存の `fetch_status` と3要素タプルを維持したまま、必要に応じてキャンセル理由を別途保持することです。

例えば、内部的に次のように区別できます。

- `user_declined_continuation`
- `application_shutdown`

これなら既存の取得状態との互換性を保ちやすくなります。具体的な格納場所は `result_data` に追加するか、`WorkerHandle` 側で管理するかをインターフェース設計で決めたいところです。

## 4. 通知の扱い

終了中に複数のモーダルダイアログを連続表示するのは避けたいです。

そこで、次のように整理するのがよいと考えます。

- 進捗通知：終了処理開始後は破棄してよい。
- 継続確認：未回答ならFalseで解除。
- 通常通知：終了中は保留。
- 保存失敗・ワーカー例外：終了前に必ずユーザーへ報告。
- 完了通知：通常の完了通知とエラー通知を重複させず、最終結果に集約する。

つまり、終了時は通知を一件ずつそのまま再生するのではなく、重要な結果をまとめて報告する方針です。

各Stageの設計書と現行実装を横断して照合した結果、基本的な責務分担は一貫しています。ただし、実装開始前に解決しておきたいインターフェース上の問題がいくつか見つかりました。

### 7-1. WorkerHandleの責務

設計書に記載された属性を整理すると、次の構成が適切です。

| 属性・機能 | 責務 |
|--------|--------|
| `thread` | ワーカースレッドの管理 |
| `gui_request_queue` | GUI要求の受け渡し |
| `cancel_event` | 協調的キャンセル |
| `done_event` | ワーカー終了の通知 |
| `result` | ワーカーの処理結果 |
| `exception` | ワーカーの例外 |

この構成自体に大きな矛盾はありません。

### 7-2. GuiRequestの責務

現行設計の3種類は適切です。

| kind | 用途 | 処理 |
|--------|--------|--------|
| `progress` | 進捗更新 | 最新値を取得してGUIへ反映 |
| `notification` | 通知 | FIFOでメインスレッドが表示 |
| `confirmation` | 継続確認 | 回答を設定してEventを解除 |

ただし、確認要求のペイロードについては、実装前に最低限次の情報を確定したいところです。

- 確認メッセージ
- 個別の `response_event`
- 回答値
- 回答確定済みかどうか

特に最後の項目は、終了処理と通常の確認ダイアログが競合した際に重要になります。

### 7-3. ワーカーの戻り値と保存結果

現行 `main.py` では、ワーカーが次の処理をまとめて実行しています。

1. API取得
2. JSON保存
3. GUI通知
4. GUI側の保存先属性更新
5. GUIのボタン状態変更

Stage 2以降では、これを分離します。

**ワーカー側**

- API通信
- 取得データの保持
- JSON保存
- 保存結果の記録
- 進捗・通知要求の登録
- 終了結果の返却

**WorkerHandle.result**

取得件数、取得状態、保存先、ファイル単位の保存成否などを保持。

**メインスレッド側**

- 保存先属性の更新
- ボタン状態の変更
- 進捗表示の終了処理
- 通知の整理・表示
- WorkerHandleの解放

この分離は、現在ワーカーが `self.last_saved_*_file_path` を直接変更している問題を解消します。

また、保存結果はファイル単位で保持し、全ファイルが成功したかどうかだけでなく、どのファイルが失敗したかも分かるようにする必要があります。

### 7-4. 起動関数のインターフェース

Stage 1の起動関数は次の形です。

`run_task_in_thread(task_function, gui_request_queue, *args, **kwargs)`

一方、共通仕様ではワーカー関数の第1引数に `WorkerHandle` を渡すことになっています。

この2つは両立できますが、実装時には次のような契約を明確にする必要があります。

- 起動関数が `WorkerHandle` を生成する。
- ワーカー関数の第1引数に生成済みの `WorkerHandle` を渡す。
- ワーカー関数の戻り値を `handle.result` に格納する。
- 例外は `handle.exception` に格納する。
- 成功・失敗を問わず `done_event` を設定する。
- `Thread.start()` の失敗は呼び出し元へ伝える。

また、現在の `main.py` は `master` を起動関数へ渡しています。これを新しいキュー所有方式へ移行する際、旧関数の互換期間をどのStageで終わらせるかも明確にしておきたいところです。

### 7-5. 進捗処理と通知処理

進捗の最新値集約方式は合理的です。

ただし、次の順序を守る必要があります。

1. ワーカーがLockを取得する。
2. 最新進捗を更新する。
3. 未登録なら進捗マーカーをキューへ登録する。
4. メインスレッドがLockを取得する。
5. 最新値を取得してマーカー登録済みフラグを解除する。

これにより、進捗更新が集中しても古い情報が大量に蓄積せず、更新の取りこぼしも防ぎやすくなります。

通知については、通常時のFIFO処理と終了時の集約処理を明確に区別する必要があります。Stage 2の「通知は原則省略しない」という方針は、Stage 4の終了時集約と矛盾しないよう、通常時と終了時の適用範囲を分けて記述するのがよいでしょう。
