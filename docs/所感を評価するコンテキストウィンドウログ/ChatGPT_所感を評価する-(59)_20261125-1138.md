`test_main.py` のフィクスチャをそのまま継承するより、Stage 4用の基底フィクスチャを `test_stage4.py` 内に設ける方が安全です。既存テストクラスの継承によって、別Stageのテストが意図せず再実行される構造を避けられます。

## 2. モック対象と実物を残す対象

| 対象 | テストでの扱い | 理由 |
|--------|--------|--------|
| `messagebox` | モック | 表示内容・回数・選択結果を制御 |
| `master.after()` / `after_cancel()` | 単体ではモック、統合では実物 | ポーリング予約とTkイベントループを区別 |
| `master.destroy()` | 単体ではモック、統合では実物 | root破棄の呼び出し順序を確認 |
| `WorkerHandle` | 実物 | Event・Lock・Queueの競合を直接検証 |
| ワーカースレッド | 原則実物 | `done_event`、join、daemon属性を検証 |
| YouTube API | モック | 実通信を避け、応答タイミングを制御 |
| JSON保存関数 | モック | 成功・失敗・例外・複数ファイルの部分成功を制御 |
| Tk Widget | 単体ではモック、統合では実物 | GUI復旧と実イベントループの検証を分離 |

特に `WorkerHandle` 自体をモック化すると、今回の重要な検証対象である `shutdown_lock`、`shutdown_decision_event`、`cancel_event` の実際の同期動作が検証できなくなります。ここは実物を使います。
