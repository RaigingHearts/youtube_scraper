スタック情報が決定的な手掛かりになりました。今回の停滞原因は、単なる処理の遅さではなく、**モーダル要求の処理が再帰的に呼び出され続けていること**です。

スタックには次の呼び出しの繰り返しが現れています。

```text
_show_modal_request
  → _drain_pending_modal_requests
    → _show_modal_request
      → _drain_pending_modal_requests
        → ...
```

発端は、テスト内で最初の通知表示中に2件目の通知要求を登録している部分です。例外発生後の後処理が、キューの次の要求を処理しようとして、さらにその処理の中から次のキュー処理を呼び出しているようです。

これはテストが検出した、実際のモーダル処理上の問題である可能性が高いです。ここでテストを単純に削除したり、タイムアウトを延ばしたりするのは適切ではありません。

ただし、ここでアプリケーション側の不具合と決めつける前に、テストコード自体も確認する必要があります。調べたところ、今回のテストに**原因となる設定ミス**が見つかりました。

### 原因

2件目の通知要求は、次のように設定されています。

```python
kind="info"
```

一方、テストで2件目の表示処理として差し替えているのは、

```python
patch.object(main.tk_notifications, "show_warning", side_effect=show_second)
```

です。

しかし、アプリケーションは `kind="info"` を受け取ると `show_info()` を呼び出します。そのため、2件目にも最初の通知用 `show_first()` が実行されます。

結果として、

1. 2件目の要求を処理する。
2. 再び `show_first()` が呼ばれる。
3. 同じ2件目の要求をキューに追加する。
4. 例外が発生する。
5. キューから同じ要求を取り出す。
6. 以降、無限に繰り返す。

という状態になります。

**現時点では、アプリケーションコードの修正は不要で、テストコードの設定ミスを直すのが妥当**と判断します。

### 修正案

2件目の通知要求を次のように変更します。

```python
kind="warning"
```

これなら既存の `show_warning` の差し替えが正しく機能し、テスト本来の目的である「例外発生後にモーダル状態が解放され、次の要求が処理されること」を検証できます。
