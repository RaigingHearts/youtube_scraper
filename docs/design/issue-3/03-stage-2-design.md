# Issue #3：Stage 2 詳細設計 — 進捗表示と通知のキュー経由化

## 1. 目的
進捗表示と通知ダイアログをメインスレッドへ集約する。

## 2. 進捗集約
進捗は最新状態が重要であり、古い更新をキューに蓄積しない。WorkerHandleに最新進捗情報、Lock、進捗マーカー登録済みフラグを保持する。

ワーカー側publish_progress()はLock内で最新情報を更新する。未処理マーカーがなければ対象WorkerHandleを識別できるマーカーをキューへ登録する。メイン側take_latest_progress()はLock内で最新情報を取得し、登録済みフラグを解除する。取得とフラグ解除の競合を防ぎ、後続更新が新しいマーカーを登録できるようにする。

## 3. 通知
notification要求は種別(info/warning/error)、タイトル、本文を持ち、通常キューでFIFO処理する。通知は原則省略せず、ダイアログはメインスレッドで1件ずつ表示する。モーダルダイアログの入れ子を避ける。

## 4. main.py
進捗マーカーから最新情報を取得してGUIへ反映する。通知要求はtk_notifications経由で表示する。ワーカー完了時の結果・保存先情報を回収し、GUI側の状態を更新する。

## 5. _scrape_comments_task()
直接after()を呼ばず、ウィジェットを参照せず、tk_notificationsを直接呼ばない。進捗はWorkerHandle経由、通知はGUI要求キュー経由とする。API通信とファイル操作はワーカー側で行い、GUI更新に必要な値は戻り値に含める。last_saved_*_file_path等はメインスレッドが更新し、プログレスバー最大値などGUI状態をワーカーから読み取らない。

## 6. APIクライアント
APIクライアント内のGUI通知はStage 3で移行するため、Stage 2完了時点では残存し得る。

## 7. 完了条件
main.py由来の進捗・通知表示がメインスレッドで行われ、進捗が集約され、ワーカーからGUIへの直接アクセスがなく、既存の取得・保存動作が維持されること。
