# Issue #3：Stage 3 詳細設計 — 継続確認のEvent方式への移行とAPIクライアントのGUI依存解消

## 1. 目的
継続確認をthreading.Event方式へ移行し、youtube_api_client.pyからTkinter依存を除去する。

## 2. 継続確認要求
ワーカーはconfirmation要求をGUI要求キューへ登録し、要求ごとのresponse_eventを待つ。要求はrequest_id、message、response_event、response、answered、response_reasonを持つ。responseの初期値は未確定を表す値とし、answered=False、response_reason=Noneとする。要求の登録・回答確定・終了時解除はWorkerHandleのconfirmation_lockで排他的に管理する。WorkerHandle.cancel_reasonも同じLockで保護し、最初に確定したキャンセル原因を保持する。

メインスレッドは確認ダイアログで回答を得た後、confirmation_lock内で要求のansweredを確認し、未回答の場合だけresponseとresponse_reasonを設定してanswered=Trueにし、response_eventを設定する。Trueは継続、Falseは中止。利用者が明示的にFalseを選んだ場合は、同じ排他区間内でWorkerHandle.cancel_reasonが未設定ならcontinuation_declinedを設定する。回答確定とEvent設定は一つの排他的操作として扱う。

ダイアログ表示例外、または表示できない状態で要求を処理した場合はFalseを既定値として一度だけ確定し、response_reason=confirmation_unavailableとする。WorkerHandle.cancel_reasonが未設定なら同じ理由を設定し、必ずEventを設定する。終了処理による解除はresponse_reason=application_shutdownとする。すでに回答済みの値・理由を上書きしない。遅延したダイアログ応答が到着してもanswered=Trueなら破棄する。

## 3. モーダルダイアログの直列化
確認、通常通知、終了確認を同時に表示しない。メインスレッドのダイアログ管理で一件ずつ処理する。確認ダイアログ表示中に終了要求が到着した場合、confirmation_lockで先に確定した側を優先する。利用者回答が先に確定していればそのresponse_reasonを維持し、終了処理は後から上書きしない。終了処理が先に未回答要求を確定した場合はapplication_shutdownを記録してFalseで解除し、遅延した利用者回答を破棄する。終了処理開始後は新しい確認ダイアログを表示しない。

## 4. APIクライアントのGUI依存解消
youtube_api_client.pyからtkinterおよびtk_notificationsのimportとダイアログ呼び出しを除去する。APIクライアントはログとresult_data内のエラー情報を維持し、利用者への通知に相当する情報を呼び出し元が判断できる形で返す。エラーを記録する責務とGUI通知を表示する責務を分離し、同一エラーの二重通知を避ける。通知方針はエラー種別と既存の利用者向け挙動を照合して定義する。

サービス生成、動画情報、チャンネル情報、コメントスレッド、返信ページの各失敗について、例外・エラー情報・ログを保持する。APIクライアントはダイアログを表示しない。ワーカー側が返却されたエラー情報をnotification要求へ変換し、メインスレッドが表示する。

## 5. 返却構造とキャンセル理由
fetch_all_comments()の既存返却タプル(result_data, fetched_count, total_expected)を維持する。既存fetch_statusと既存result_dataの主要構造を維持し、新しい必須戻り値を追加しない。

fetch_status="cancelled"は従来どおり維持する。APIクライアントはBoolean確認応答だけから理由を推測せず、WorkerHandleにも依存しない。ワーカータスクはfetch_all_comments()から戻った後、confirmation_lockで確定済みのWorkerHandle.cancel_reasonを読み、キャンセル結果のresult_data["cancel_reason"]へ反映する。理由はcontinuation_declined（利用者が明示的に中止）、application_shutdown（アプリ終了）、confirmation_unavailable（確認ダイアログの例外・表示不能）とする。キャンセル以外では項目を省略する。cancel_reasonは補足情報とし、既存利用者がfetch_statusだけを参照しても従来どおり動作する。

## 6. Stage 4への準備
Stage 4でfetch_all_comments()にcancel_eventを渡す。APIクライアントはEventだけを扱い、TkinterやWorkerHandleに依存しない。API要求の実行中は強制中断せず、要求の前後でEventを確認する。

## 7. 旧方式の整理
confirm_continuation_gui()、BooleanVar、wait_variableを利用する旧方式は全呼び出し箇所の移行後に削除する。旧関数の削除は新旧呼び出し箇所の検索・確認後に行い、未移行の利用者を残さない。

## 8. 完了条件
Event確認が正常・異常・終了競合の各経路で一度だけ解除され、APIクライアントにGUI依存がなく、既存の返却タプル・取得結果・エラー状態の意味が維持されること。
