# Issue #3：Stage 3 詳細設計 — 継続確認のEvent方式への移行とAPIクライアントのGUI依存解消

## 1. 目的
継続確認をthreading.Event方式へ移行し、youtube_api_client.pyからTkinter依存を除去する。

## 2. 継続確認要求
ワーカーはconfirmation要求を生成し、confirmation_lock内でWorkerHandle.pending_confirmationsへrequest_idをキーとして登録した後、GUI要求キューへ登録し、要求固有のresponse_eventを待つ。登録とキュー投入は同じ排他区間で行い、登録済みなのにキューへ投入されない中間状態を作らない。要求はrequest_id、message、response_event、response、answered、response_reasonを持つ。responseの初期値は未確定を表す値とし、answered=False、response_reason=Noneとする。ワーカーはEvent解除後、finally相当の経路でconfirmation_lockを取得してpending_confirmationsから当該request_idを解除する。要求の登録・回答確定・終了時解除・登録解除はWorkerHandleのconfirmation_lockで排他的に管理する。WorkerHandle.cancel_reasonも同じLockで保護し、最初に確定したキャンセル原因を保持する。

メインスレッドは確認ダイアログで回答を得た後、confirmation_lock内で要求のansweredを確認し、未回答の場合だけresponseとresponse_reason=user_responseを設定してanswered=Trueにし、response_eventを設定する。user_responseは利用者が実際にダイアログへ回答したことを示し、True/Falseの両方で使用する。Trueは継続、Falseは中止。利用者が明示的にFalseを選んだ場合は、同じ排他区間内でWorkerHandle.cancel_reasonが未設定ならcontinuation_declinedを設定する。回答確定とEvent設定は一つの排他的操作として扱う。

ダイアログ表示例外、または表示できない状態で要求を処理した場合はFalseを既定値として一度だけ確定し、response_reason=confirmation_unavailableとする。WorkerHandle.cancel_reasonが未設定なら同じ理由を設定し、必ずEventを設定する。終了処理が未回答要求を解除する場合はFalse、response_reason=application_shutdownとする。response_reasonは確認要求の回答経路、cancel_reasonは取得処理を中止させた原因を表す別の値である。cancel_reasonの値はcontinuation_declined、confirmation_unavailable、application_shutdownに限定し、最初に確定した値を上書きしない。すでに回答済みの値・理由を上書きしない。遅延したダイアログ応答が到着してもanswered=Trueなら破棄する。

## 3. モーダルダイアログの直列化
確認、通常通知、終了確認を同時に表示しない。メインスレッドはダイアログ表示中フラグを表示呼び出し前に設定し、ダイアログを閉じるまで解除しない。Tkinterのモーダルダイアログは内部イベントループを動かすため、その間に再入したポーリング処理は新たなnotification/confirmationダイアログを開かず、要求をFIFOの保留列へ退避する。ダイアログ終了後に保留列の先頭から一件ずつ表示する。進捗更新などダイアログを伴わない要求は既存の処理規則に従ってよい。表示処理はtry/finallyでフラグを必ず解除し、表示例外はログへ記録する。確認要求の表示に失敗した場合はconfirmation_unavailableとしてFalseでEventを解除する。確認ダイアログ表示中に終了要求が到着した場合、confirmation_lockで先に確定した側を優先する。利用者回答が先に確定していればそのresponse_reasonを維持し、終了処理は後から上書きしない。終了処理が先に未回答要求を確定した場合はapplication_shutdownを記録してFalseで解除し、遅延した利用者回答を破棄する。終了処理開始後は新しい確認ダイアログを表示しない。

## 4. APIクライアントのGUI依存解消
youtube_api_client.pyからtkinterおよびtk_notificationsのimportとダイアログ呼び出しを除去する。APIクライアントはログとresult_data内のエラー情報を維持し、利用者への通知に相当する情報を呼び出し元が判断できる形で返す。エラーを記録する責務とGUI通知を表示する責務を分離し、同一エラーの二重通知を避ける。通知方針はエラー種別と既存の利用者向け挙動を照合して定義する。

サービス生成、動画情報、チャンネル情報、コメントスレッド、返信ページの各失敗について、例外・エラー情報・ログを保持する。APIクライアントはダイアログを表示しない。ワーカー側が返却されたエラー情報をnotification要求へ変換し、メインスレッドが表示する。通知対象は既存挙動を基準にし、サービス構築失敗・動画情報取得APIエラー・チャンネル情報取得APIエラー・返信ページ取得失敗・コメントスレッド取得失敗はerror、動画が見つからない(videoNotFound)はwarningとする。commentsDisabledは専用の取得不可通知としてwarningを一度だけ表示する。動画情報が空であった場合やチャンネル情報が空であった場合など、従来ログのみだった事象は、エラー配列に記録されていても単独では新たなダイアログ通知に昇格させない。通知対象としたエラーはAPIクライアント側で通知済みフラグまたは同等の機械可読情報を付与し、ワーカー側で同一事象を重複変換しない。APIクライアントの戻り値の既存構造と3要素タプルは維持し、必要な通知分類情報は既存errors要素の追加フィールド等、後方互換な方法で表現する。

## 5. 返却構造とキャンセル理由
fetch_all_comments()の既存返却タプル(result_data, fetched_count, total_expected)を維持する。既存fetch_statusと既存result_dataの主要構造を維持し、新しい必須戻り値を追加しない。

fetch_status="cancelled"は従来どおり維持する。APIクライアントはBoolean確認応答だけから理由を推測せず、WorkerHandleにも依存しない。ワーカータスクはfetch_all_comments()から戻った後、confirmation_lockで確定済みのWorkerHandle.cancel_reasonを読み、キャンセル結果のresult_data["cancel_reason"]へ反映する。理由はcontinuation_declined（利用者が明示的に中止）、application_shutdown（アプリ終了）、confirmation_unavailable（確認ダイアログの例外・表示不能）とする。キャンセル以外では項目を省略する。cancel_reasonは補足情報とし、既存利用者がfetch_statusだけを参照しても従来どおり動作する。

## 6. Stage 4への準備
Stage 4でfetch_all_comments()にcancel_eventを渡す。APIクライアントはEventだけを扱い、TkinterやWorkerHandleに依存しない。API要求の実行中は強制中断せず、要求の前後でEventを確認する。

## 7. 旧方式の整理
confirm_continuation_gui()、BooleanVar、wait_variableを利用する旧方式は全呼び出し箇所の移行後に削除する。旧関数の削除は新旧呼び出し箇所の検索・確認後に行い、未移行の利用者を残さない。

## 8. 完了条件
Event確認が正常・異常・終了競合の各経路で一度だけ解除され、pending_confirmationsが解放後に残らず、応答値と理由が上書きされないこと。モーダルダイアログの再入が防止され、保留要求のFIFO順が維持されること。APIクライアントにGUI依存がなく、従来通知対象だった事象だけが対応する通知種別で一度通知され、従来ログのみだった事象が通知へ昇格しないこと。既存の返却タプル・取得結果・エラー状態の意味が維持されること。
