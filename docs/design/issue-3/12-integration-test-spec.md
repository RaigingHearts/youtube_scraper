# Issue #3／Issue #20 統合テスト仕様

## 1. 目的

Stage 1～4で導入・移行した機能を組み合わせ、個別Stageでは検出しにくい連携不具合、競合、既存機能への回帰を検証する。Stage単独のテスト仕様を置き換えるものではない。

## 2. 共通条件

- YouTube API、ネットワーク、長時間待機はモック化する。
- ファイル保存は一時ディレクトリまたは制御可能なモックを使用する。
- GUI統合試験は実Tkイベントループを使用し、GUI不要の単体テストとは分ける。
- スレッドの順序制御はEvent／Barrier等を使用し、任意のsleepへの依存を避ける。
- Python 3.8.10を基準とする。

## 3. Stage 1統合シナリオ

- ワーカー起動からGUI要求登録、メインスレッド処理、完了検知、結果・例外回収までの一連の流れ。
- 50件を超えるGUI要求、要求処理例外、未知の要求種別を含む場合もポーリングが継続すること。
- ワーカー完了時にキュー残件がある場合、残件処理後に完了処理へ進むこと。
- Thread.start()失敗後にGUI状態を復旧し、再実行できること。
- 旧方式の呼び出しと新方式の呼び出しが移行期間中に混同されないこと。

## 4. Stage 2統合シナリオ

- 進捗更新が連続した場合、最新値がGUIへ反映され、マーカーの重複や更新取りこぼしがないこと。
- progressとnotificationが混在しても処理順・表示内容が正しいこと。
- API取得中にGUIが応答し、ワーカーがGUI所有状態を直接変更しないこと。
- 通知表示例外後も後続通知とワーカー完了処理が継続すること。

## 5. Stage 3統合シナリオ

- 継続確認Trueで取得継続、Falseで中止し、応答Eventが確実に解除されること。
- 確認要求が複数ある場合にEvent・応答が混線せず、pending_confirmationsへの登録・解除に漏れがないこと。
- 利用者のTrue/False回答ではresponse_reason=user_response、Falseの場合のみcancel_reason=continuation_declinedとなること。終了解除・表示不能では各々application_shutdown・confirmation_unavailableがresponse_reasonとcancel_reasonへ正しく反映されること。
- モーダルダイアログ表示中にポーリングが再入しても新しいダイアログを開かず、保留した通知・確認要求をFIFOで処理すること。ワーカー例外通知も同じGUI要求経路で表示し、保留中のモーダル要求が残る間は完了後処理を確定しないこと。
- APIクライアントがGUIを操作せず、戻り値・エラー情報を呼び出し元へ返すこと。
- 従来通知対象だったAPIエラーだけが適切な種別で一度通知され、従来ログのみだった事象が通知に昇格しないこと。
- APIエラー、確認ダイアログ例外、確認待機中の状態を組み合わせても二重通知・待機残りがないこと。

## 6. Stage 4統合シナリオ

- API通信中、ページ間待機中、確認待機中、保存開始前、保存中に終了要求が発生した場合の状態遷移。
- 保存して終了／追加保存せず終了／終了を取り消す各選択。
- 終了確認と保存開始、自然終了、確認応答が競合した場合の一度限りの確定。
- 部分取得、複数ファイル保存、ファイル単位失敗、予期しない保存例外の組み合わせ。
- 未処理GUI要求、通知サマリー、WorkerHandle解放、root破棄の順序。

## 7. 既存機能の回帰

少なくとも次を既存仕様どおり維持することを確認する。

- 動画ID入力・URL解析・入力検証。
- APIキー設定・取得処理の開始。
- 動画情報、チャンネル情報、コメント、返信コメントの取得結果。
- 既存fetch_status、返却タプル、result_dataの互換性。
- JSON保存形式、ファイル名・保存先の規則、保存結果の表示。
- ログ表示、保存済みJSONを開く操作。
- 取得完了・部分取得・コメント無効・失敗時の利用者向け通知。

Issue #10の進捗件数推定・超過問題など、Issue #3の対象外機能は本テストで仕様変更しない。

## 8. 統合完了条件

- Stage 1～4の各Stageテストが合格している。
- 本書のStage間連携・異常系・競合シナリオが合格している。
- 既存回帰テストが成功している。
- 実デスクトップ環境で受け入れ確認を行い、API通信中もGUIが応答し、終了時にワーカー待機やEvent待機が残らない。
- 未解決事項、実行できなかったテスト、環境制約を明記し、未実施を合格として扱わない。


## 9. Stage 3実装に基づく追加確認事項（Issue #20引き継ぎ）

既存のStage 3統合シナリオに加え、実装コードとの対応を確認する。

- youtube_api_client.py の通知依存除去に伴い、既存テストの tk_notifications patchを更新し、result_data["notifications"] の分類レコードを検証する。
- 通知レコードの stage/kind/title/message、従来の利用者向け通知対象、ログのみの事象、commentsDisabledの専用warningを区別する。
- fetch_all_comments() の3要素タプル、既存 fetch_status、取得結果、取得件数の互換性を確認する。
- 終了処理と確認回答の競合では、先に確定したresponseとresponse_reasonを保持し、後から確定した終了理由はcancel_reasonへ別途記録する。
- 終了後にFIFO保留列へ残った古い確認要求がダイアログ表示されず、Event待機が残らないことを確認する。確認要求のdisplay_started設定と終了処理の競合では、Lock内で先に確定した表示開始・終了解除のどちらか一方だけが成立し、表示開始済み要求の応答値を終了処理が上書きしないことを確認する。

これらはIssue #20で実装・実行する検証項目であり、現時点で合格済みではない。
