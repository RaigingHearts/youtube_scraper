# Issue #3／Issue #20 共通テスト仕様

## 1. 目的・適用範囲

Stage 1～4を通じて共通するスレッド境界、GUI要求、ワーカー状態、例外処理、結果回収の契約をテストする。共通契約の規範は `09-cross-stage-interface.md` とし、本書はテスト観点を整理する。

## 2. スレッド境界

- Tkinterのウィジェット、Tk変数、ダイアログ、root.after()の実行主体がメインスレッドである。
- ワーカーはTkinterオブジェクトを直接操作しない。
- GUI要求の登録はワーカー側から可能だが、要求の取り出しとGUI操作はメインスレッド側で行う。
- GUI所有状態はメインスレッドが更新し、ワーカーは結果データとして返す。
- Stage 1では基盤導入前から残る旧処理経路を区別し、Stage 2・3の移行完了後にアプリケーション全体の境界条件を合格判定する。

検証では、実行スレッドIDの記録、Tkinter操作を行うモックの呼び出しスレッド記録、静的検索を組み合わせる。静的検索だけでスレッド境界を合格としない。

## 3. GUI要求キュー

- 要求はFIFOで処理する。ただしprogress要求は最新値取得用のマーカーであり、すべての中間進捗値を表示する契約ではない。
- 1回のポーリング上限を守り、残件を後続ポーリングで処理する。
- 要求1件の失敗、未知のkind、不正な要求オブジェクトが後続処理を停止させない。
- notificationは種類・タイトル・本文を保持し、表示順を維持する。
- confirmationは要求単位で応答Eventを持ち、回答を一度だけ確定する。
- payloadにはTkinterオブジェクトを含めない。

## 4. WorkerHandleとライフサイクル

- 1ワーカーにつき1つのWorkerHandleを用いる。
- thread、result、exception、done_eventを正しく保持する。
- 正常・例外のどちらでもdone_eventを設定する。
- Thread.start()失敗はワーカー実行中の例外と区別する。
- done_event後も未処理GUI要求と結果等を回収するまでWorkerHandleを解放しない。
- 同時実行ワーカー数の上限を守り、完了後に再実行できる。
- Stage 4ではdaemon設定、cancel_event、終了待ち、root破棄順序も含めて検証する。

## 5. Event・競合・一度限りの確定

- Eventは待機側が永久に停止しないよう、成功・失敗・終了の全経路で設定条件を検証する。
- confirmationの回答と終了解除が競合しても、response、response_reason、cancel_reasonが一度だけ確定する。
- Lock保持中にEvent待機やGUIダイアログ表示を行わない。
- 競合テストはBarrier/Event等で順序を制御し、タイミング依存のsleepを避ける。

## 6. 例外・後始末

- ワーカー例外をWorkerHandle.exceptionへ保持し、GUI側が通知・状態復旧を行う。
- 例外通知の表示自体が失敗しても、GUI状態の復旧とWorkerHandle解放を妨げない。
- GUI要求1件の例外が後続要求や次回ポーリングを停止させない。
- 保存処理の個別失敗と予期しない全体例外を区別する。
- root破棄後にafter()を登録しない。

## 7. テストダブル・外部依存

- YouTube APIクライアント、API応答、ネットワーク待機はモック化する。
- Tk通知・ダイアログは呼び出しと実行スレッドを検証できるモックを用意する。
- ファイル保存は一時ディレクトリまたは保存関数モックを使い、保存成功・失敗・部分成功を制御する。
- Thread.start()失敗、ワーカー例外、Event待機、GUI要求処理例外を再現可能にする。
- 実APIキーや実YouTube APIへのアクセスをテスト前提にしない。

## 8. Stage別の適用時期

- Stage 1：データ構造、ワーカー起動・終了、キュー処理基盤。
- Stage 2：進捗・通知の実処理移行、GUI所有状態のメインスレッド更新。
- Stage 3：継続確認Event、APIクライアントのGUI非依存性。
- Stage 4：協調的キャンセル、保存判断バリア、終了処理、root破棄。

全Stage完了後に、アプリケーション全体のスレッド境界とライフサイクルを統合的に再検証する。
