# Issue #3：Stage 1 テスト仕様 — GUI要求キューとワーカー管理

## 1. 目的・対象

Stage 1で導入したGUI要求基盤とワーカー管理の振る舞いを検証する。対象は次のとおり。

- `GuiRequest`、`WorkerHandle`、`run_task_in_thread()`
- `WorkerHandle.publish_progress()`／`take_latest_progress()`
- `main.py` のGUI要求キュー所有、ポーリング、要求振り分け
- ワーカー起動、完了・例外回収、GUI状態復旧
- 既存呼び出しとの移行期間中の互換経路

本書はテスト仕様であり、テストコードそのものではない。テストコードの作成・実行環境整備はIssue #20で行う。

## 2. Stage 1の検証範囲と後続Stageへの切り分け

Stage 1は共通基盤の導入段階であり、既存の取得処理すべてをキュー方式へ移行する段階ではない。

- Stage 1で検証する：要求データ構造、ワーカー管理、キューのポーリングと振り分け、起動失敗・例外・正常終了の回収。
- Stage 2で検証する：実際の取得処理から進捗・通知をキュー経由に移行し、ワーカーからの直接GUI操作およびGUI所有状態の直接更新を除去する。
- Stage 3で検証する：継続確認のEvent方式への移行、APIクライアントのTkinter依存除去。
- Stage 4で検証する：協調的キャンセル、終了判断、保存方針、ワーカー終了待ち、root破棄。

したがって、Stage 1のテストで「アプリケーション全体からワーカーのTkinter直接操作がなくなった」と判定してはならない。現行の `_scrape_comments_task()` には旧進捗コールバック、`master.after()`、旧継続確認、通知表示、およびGUI所有属性への代入が残っており、後続Stageで移行・検証する。

## 3. データ構造の単体テスト

### 3.1 GuiRequest

- `kind`、`payload`、`request_id` が指定値または規定の初期値で保持される。
- `request_id` が要求ごとに生成され、複数要求間で重複しない。
- `payload` のデフォルト辞書がインスタンス間で共有されない。
- `confirmation` の場合に要求ごとに独立した `response_event` が生成される。
- `response`、`answered`、`response_reason` の初期状態を確認する。
- 進捗・通知等の実際の要求生成箇所がTkinterオブジェクトをpayloadへ格納しないことを確認する。

注：現行の `GuiRequest` はpayload内のTkinterオブジェクトを実行時に拒否するバリデーションを持たない。したがって、最後の項目は要求生成側の契約テストとして扱い、データクラス自体が不正payloadを拒否すると仮定しない。

### 3.2 WorkerHandle

- `cancel_event`、`done_event`、`shutdown_decision_event` が初期状態でunsetである。
- `result`、`exception`、`latest_progress`、`cancel_reason` 等の初期値を確認する。
- `partial_result` が `{"saved_files": []}` で初期化される。
- 各Event、Lock、辞書、リストがインスタンス間で共有されない。
- `pending_confirmations` が独立した辞書である。
- `thread` が未設定状態から開始する。

### 3.3 進捗集約プリミティブ

- `publish_progress()` が最新値を置換する。
- マーカー未登録時にprogress要求を1件登録し、登録済みの場合は重複登録しない。
- `take_latest_progress()` が最新値を返し、マーカー登録可能状態へ戻す。
- マーカー取得直前・直後の更新が取りこぼされず、後続マーカーまたは取得済み最新値として反映される。
- 同時更新時もLockにより状態が破損しない。

注：このプリミティブの単体検証と、実際の取得処理がこれを利用していることの検証は別である。実取得処理への接続はStage 2で確認する。

## 4. ワーカー起動・実行・終了テスト

### 4.1 新方式

- `queue.Queue` を渡した場合、`WorkerHandle` が生成される。
- ワーカー関数へ `WorkerHandle` が第1引数として渡される。
- 位置引数・キーワード引数が正しく引き渡される。
- ワーカーが呼び出し元とは異なるスレッドで実行される。
- スレッド名が規定どおり設定され、Stage 1ではdaemon属性がTrueである。
- ワーカーの戻り値が `handle.result` に保持される。
- ワーカー例外が `handle.exception` に保持され、ログに記録される。
- 正常終了・例外終了のどちらでも `done_event` が設定される。
- `queue.Queue` 以外を渡した場合、スレッド起動前にTypeErrorとなる。

### 4.2 旧方式の互換経路

- 第1引数がTkinterの `tk.Misc` である旧呼び出し形式を識別する。
- 旧方式では内部キューを生成し、旧タスク関数へWorkerHandleを追加引数として渡さない。
- 旧方式の既存呼び出しが移行期間中に実行可能である。
- 新方式と旧方式の判定を取り違えない。

### 4.3 起動失敗

- `Thread.start()` が例外を送出した場合、その例外が呼び出し元へ伝播する。
- 起動失敗時に `done_event` が設定される。
- 起動失敗をワーカー関数の例外終了として扱わない。
- `main.py` が起動失敗を捕捉し、GUI状態を復旧する。
- 起動失敗後に再実行できる。

## 5. GUI要求キューとポーリング

- アプリケーションがキューを1つ所有し、ワーカーとGUI側が同じキューを参照する。
- 初回ポーリングがメインスレッドから50ms後に予約される。
- 同じポーリングが重複予約されない。
- 1回のポーリングで最大50件を処理する。
- 50件処理後に残件があれば次回ポーリングで処理を継続する。
- 空キューでは正常に終了し、次回ポーリングを予約する。
- 要求1件の処理で例外が発生しても、後続要求の処理と次回ポーリングが継続する。
- 不正オブジェクトおよび未知の要求種別をログへ記録し、後続要求を停止させない。
- root破棄後に `after()` の登録を試みた場合、TclErrorを捕捉する。

### 5.1 要求種別の振り分け

- progress：現在のWorkerHandleから最新進捗を取得し、GUI側更新処理へ渡す。
- notification：info／warning／errorを種類に応じて振り分ける。
- confirmation：Stage 1では実ダイアログを表示せず、未対応要求をFalseで解除し、Event待機を残さない。
- 未知のkind：警告ログを記録し、その要求のみを処理対象外とする。

## 6. ワーカーライフサイクル・GUI復旧

- 既存WorkerHandleが保持されている間は新規ワーカー起動を拒否する。
- `done_event` が設定されても、GUI要求キューに残件がある間は完了処理を行わない。
- キューが空になった後に完了処理を行う。
- 正常終了時にWorkerHandleを解放し、取得ボタン等のGUI状態を復旧する。
- 例外終了時に例外を回収・通知し、通知表示自体が失敗してもGUI状態を復旧する。
- 完了後に次のワーカーを起動できる。
- 起動失敗後に内部参照が残らず、次の起動を妨げない。

## 7. GUI統合テスト

Tkイベントループを使用し、YouTube API通信とファイル保存はモック化する。

- 正常終了、ワーカー例外、Thread.start失敗の各経路。
- GUI要求の登録からメインスレッドでの処理まで。
- 50件を超える要求の継続処理。
- 要求処理中の例外後もイベントループとポーリングが継続すること。
- ワーカー完了後に未処理要求が残っている場合の完了処理保留。
- GUI状態復旧後の再実行。

GUI不要の単体テストと実Tkイベントループを使う統合テストは分ける。実API通信は行わない。

## 8. 実装後の照合事項・既知の差異

2026-11-22に確認したStage 1ブランチの実装に基づく照合事項。

- `GuiRequest`、`WorkerHandle`、新旧方式を扱う `run_task_in_thread()`、キュー所有、50ms／最大50件のポーリング、要求振り分け、完了・例外回収が実装されている。
- `publish_progress()`／`take_latest_progress()` は実装されているが、現行の取得処理からの利用はStage 2で移行する。
- confirmation要求はStage 1ではFalseで解除する仮実装であり、利用者に確認する本来のEvent応答処理はStage 3の対象である。
- `_scrape_comments_task()` に残る旧方式のTkinter操作とGUI所有属性の更新は、Stage 1の合否条件に含めず、Stage 2・3の移行対象として追跡する。
- 起動失敗時、`_start_scrape_process()` は取得ボタンと進捗表示を復旧する一方、起動直前に無効化した `open_json_button` の復旧が確認できない。Stage 1設計の「ボタン状態の復旧」と一致しないため、起動失敗時の状態復旧テストで確認し、Stage 1完了判定前に修正要否を解消する。
- 現行の `_finish_worker()` は `result` をGUI側の取得結果へ反映せず、主に例外を回収している。Stage 1ではWorkerHandleへのresult格納を検証し、取得結果のGUI所有状態への反映は後続Stageの結果契約と合わせて検証する。
