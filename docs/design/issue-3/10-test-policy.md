# Issue #3／Issue #20 テスト基本方針

## 1. 目的

Issue #3のStage 1～4で実施するアプリケーション改修について、期待動作と検証条件を実装前に定義し、Issue #20でのテストコード実装・統合検証へ一貫して引き継ぐ。

本書はテスト仕様ドキュメント群全体の基本方針を定める。個別機能の詳細な期待動作は、各Stageテスト仕様および共通テスト仕様を正とする。

## 2. Issue間の役割分担

### Issue #3
- Stage 1～4のアプリケーション改修を担当する。
- 各Stageの改修設計と並行して、期待動作、異常系、境界条件、受け入れ条件をテスト仕様へ記録する。
- 各Stageで既存回帰テストを実行可能な範囲で行い、実行結果と制約を記録する。
- 新規テストコードの本格的な実装は担当しない。

### Issue #20
- Issue #3から引き継いだテスト仕様を基準に、新規テストコードを実装する。
- 必要なモック、GUI統合テスト環境、テスト配置・命名・実行方法を整備する。
- Stage 1～4の新規テストと既存回帰テストを統合実行し、不具合を検出・修正する。

既存回帰テストの成功を、新規機能の検証済みという意味に読み替えない。

## 3. テスト分類

- 単体テスト：データ構造、ワーカー管理、キュー処理、Event、状態遷移などを個別に検証する。
- コンポーネントテスト：main.pyとワーカー管理モジュール等、隣接する構成要素の連携を検証する。
- GUI統合テスト：実Tkイベントループ上でGUI要求、ダイアログ、ワーカー完了、終了制御を検証する。
- 回帰テスト：既存の取得機能、API結果、設定、保存、ログ等に意図しない影響がないことを検証する。
- 受け入れ確認：実際のデスクトップ環境で、利用者操作と長時間処理中の応答性を確認する。

## 4. テスト設計原則

- 期待動作と合否条件を実装前に定義する。
- 設計変更時は、改修設計・共通インターフェース・テスト仕様の整合を同時に確認する。
- 正常系だけでなく、異常系、境界条件、競合、重複要求、順序、後始末を含める。
- スレッド・Eventのテストは可能な限り同期プリミティブを使い、任意のsleepに依存した不安定なテストを避ける。
- 外部API通信はモック化し、テストから実YouTube APIへアクセスしない。
- ファイル保存は一時ディレクトリまたはモックを使用し、利用者の実データを変更しない。
- テストが失敗した場合に原因を特定できるよう、テスト対象・前提・期待結果を明確にする。
- Python 3.8.10との互換性を維持し、新規依存の追加はIssue #20で必要性を確認してから決定する。

## 5. Stageごとの追跡

Stage 1～4のテスト仕様は各Stageの改修設計に対応させる。Stage単独の検証とStage間の統合検証を区別し、後続Stageで初めて導入される機能を前Stageの失敗条件として扱わない。

共通契約は `09-cross-stage-interface.md` および `11-common-test-spec.md` を参照する。Stage間の組み合わせは `12-integration-test-spec.md` で管理する。

## 6. テスト結果の記録

各実行結果には少なくとも次を記録する。

- 実行日時、ブランチ・コミット
- Pythonおよびテストランナーのバージョン
- 実行コマンド、対象範囲、検出件数
- 成功・失敗・スキップ件数
- 失敗時の概要と関連Issue
- モック・GUI環境等の実行条件
- 既存回帰テストか新規機能テストかの区別

利用者が実行した結果は「利用者報告」、アシスタントまたはCI等が実際に実行して確認した結果は、その実行主体を明記する。

## 7. 完了・引き継ぎ

Stage 4のアプリケーション改修完了後、Stage 1～4の仕様、共通仕様、統合仕様、環境仕様を一式として整理し、文書間の参照・用語・合否条件を確認してIssue #20へ引き継ぐ。仕様と実装に未解決の差異がある場合は、未解決事項として明記し、暗黙に合格扱いしない。

Stage 1～4それぞれの「実装完了」と「新規テスト検証完了」は区別する。実装完了はアプリケーション改修、設計との整合確認、実行可能な既存回帰テストの結果記録を基準に判断し、新規テストコードの実装・実行を前提条件としない。新規テスト検証完了は、Issue #20で該当Stageの新規テストおよび統合テストを実装・実行し、結果を記録した時点で別途判断する。既存回帰テストの成功だけをもって新規機能の検証完了とはしない。


## 8. Stage実装とテスト検証の完了状態
Stageごとの進捗記録では、少なくとも次の状態を混同しない。
- **実装完了**：対象Stageのアプリケーション改修と設計整合確認が完了し、実行可能な既存回帰テストの結果・制約が記録されている。
- **新規テスト仕様確定**：対象Stageの期待動作・異常系・境界条件・受け入れ条件がテスト仕様書に反映されている。
- **新規テスト検証完了**：Issue #20で新規テストコードが実装・実行され、結果が記録されている。
- **統合検証完了**：Stage 1～4の新規テストと既存回帰テストを統合して実行し、結果が記録されている。

Issue #3のStage 1～4の実装作業中は、各Stageの新規テスト仕様を先行して整備するが、新規テストコードの本格実装は行わない。Issue #20への引き継ぎ後に、上記の新規テスト検証・統合検証を進める。
