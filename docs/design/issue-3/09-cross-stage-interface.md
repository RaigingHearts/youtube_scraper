# Issue #3：Stage間インターフェース・整合性確認書

## 1. 目的と優先順位
Stage 1〜4の共通インターフェースと処理順序を定義し、実装時の解釈差を防ぐ。本書はStage間の共通契約の規範文書とする。各Stage設計書・テスト仕様書と矛盾がある場合は、本書の共通契約を優先し、実装前に該当文書を同期修正する。

## 2. WorkerHandle
WorkerHandleは一つのワーカー実行のライフサイクルを管理する。最低限、次を保持する。
- thread：実行スレッド
- gui_request_queue：GUI要求キュー
- cancel_event：協調的キャンセル要求
- done_event：ワーカー関数の終了通知
- result：ワーカー関数の戻り値
- exception：未処理例外
- partial_result：処理途中で確定した保存結果を保持する構造化データ。少なくともsaved_filesの空リストを持つ
- progress_lock、latest_progress、progress_marker_queued：進捗集約
- confirmation_lockおよびpending_confirmations：未回答確認要求。各要求はresponse_reasonとdisplay_startedを持つ。display_startedは確認ダイアログ表示開始をLock内で確定したことを示す
- shutdown_lock、shutdown_decision_event、shutdown_pending：終了判断バリア
- save_policy、save_started：終了時保存方針と保存開始状態
- cancel_reason：最初に確定したキャンセル原因の補足情報。confirmation_lockで保護し、後から上書きしない
- exception_notification_queued：ワーカー例外通知をGUI要求キューへ一度だけ登録したことを示す

Eventは初期状態unset、フラグはFalse、result/exception/latest_progressは未設定状態から開始する。partial_resultは保存処理開始前に初期化し、main.pyはdone_event後に読み取る。実装上のデータ型はPython 3.8.10で扱える標準型とし、新規外部依存を追加しない。

## 3. GuiRequest共通仕様
GuiRequestはkind、payload、request_idを持ち、payloadにTkinterオブジェクトを含めない。request_idはWorkerHandle内で一意とし、要求と応答の対応付けに用いる。
- progress：payloadは空または進捗対象の識別情報。進捗値本体はWorkerHandle.latest_progressに保持する。
- notification：payloadはkind(info/warning/error)、title、messageを持つ。
- confirmation：payloadはmessageを持ち、要求本体はresponse_event、response、answered、response_reason、display_startedを保持する。response_eventは要求ごとに独立する。response_reasonはuser_response（利用者がTrue/Falseを回答）、application_shutdown（終了処理が表示開始前の未回答要求を解除）、confirmation_unavailable（ダイアログ例外・表示不能で解除）を表す。display_startedはconfirmation_lock内で表示開始と終了処理の競合を調停する境界であり、Trueの要求は終了処理が回答を上書きせず、GUI側の回答または表示例外で完了する。response_reasonは回答経路であり、キャンセル原因cancel_reasonとは別の値である。

未知のkindはログへ記録し、その要求だけを失敗扱いとして後続要求の処理を継続する。

## 4. ワーカー起動・終了契約
run_task_in_thread(task_function, gui_request_queue, *args, **kwargs)はWorkerHandleを生成し、task_functionへWorkerHandleを第1引数として渡す。ラッパーは戻り値をresultへ格納し、未処理例外をexceptionへ格納してログに記録する。いずれの場合もfinallyでdone_eventを設定する。
Thread.start()失敗は起動呼び出し元へ伝播させ、main.pyがGUI状態を復旧できるようにする。起動失敗をワーカー関数の例外終了として偽装しない。ワーカー関数の例外はdone_eventで終了を通知した後、メインスレッドがexceptionを回収して利用者向け通知を行う。

同時実行ワーカーは1つ。done_event後も要求・result・exception・partial_resultの回収とGUI後処理が終わるまではWorkerHandleを解放しない。

## 5. 進捗契約
publish_progress()はprogress_lock内でlatest_progressを置換する。progress_marker_queued=Falseならprogressマーカーをキューに登録し、同じLock保護区間でTrueにする。take_latest_progress()は同じLock内で最新値を取得し、progress_marker_queued=Falseに戻す。キュー登録・最新値更新・マーカーフラグの変更を一体として扱い、取りこぼしを防ぐ。進捗マーカーは最新値を取得するための通知であり、各更新履歴を表すものではない。

## 6. 通知契約
通常稼働時はnotification要求をFIFOで一件ずつメインスレッドに表示する。モーダルダイアログ表示前に表示中フラグを設定し、表示終了時はtry/finallyで解除する。モーダルダイアログのネストしたイベントループからポーリングが再入した場合、notification/confirmation要求を新たに表示せずFIFOの保留列へ退避し、現在のダイアログ終了後に順次処理する。表示中に新しいダイアログを開かない。1件の表示例外はログに記録し、後続要求の処理を継続する。確認ダイアログの表示例外はconfirmation_unavailableとして要求をFalseで解除する。ワーカー例外もnotification GuiRequestとしてキューへ登録し、キューとFIFO保留列の両方が空でモーダル表示中でない場合に限って完了後処理を確定する。同一事象について複数経路から重複する通知要求を登録・表示しない。

Stage 2の移行期間に限り、通知の発生元と責務を次のように定める。
- youtube_api_client.py：APIサービス構築・API取得に起因する既存の利用者向け通知を担当する。Stage 2では既存tk_notifications呼び出しを移行例外として維持する。
- _scrape_comments_task()：fetch_result["errors"]をそのままnotification要求へ変換せず、APIクライアントが通知する同一事象を再通知しない。保存結果やタスク固有の状態など、APIクライアントの通知とは異なる事象だけをnotification要求として登録する。
- main.py：notification要求を表示し、必要に応じてワーカー例外を通知する。ただし、APIクライアントが既に通知した同一事象を重複表示しない。

同一事象の通知元を一つに定められない場合は、既存のAPIクライアント通知を優先し、タスク側の重複通知を抑止する。このStage 2限定の責務分担は、Stage 3でAPIクライアントのGUI依存を撤去した後、APIクライアントがエラー情報を返し、ワーカーがnotification要求を登録する共通契約へ移行する。
終了処理開始後は個別の通知ダイアログを表示せず、通知要求をFIFOで退避する。ワーカー終了後、種類・本文・発生順を保った一つの終了時サマリーとして報告する。情報・警告・エラーのいずれも黙って破棄しない。通知がない場合はサマリーを表示しない。この終了時の退避・集約・個別通知抑制はStage 4の責務とする。Stage 2では通常稼働中のFIFO表示を扱い、Stage 4の終了制御を先取りしない。

## 7. 継続確認契約
ワーカーはconfirmation_lock内で要求をpending_confirmationsへ登録し、同じ排他区間でGUI要求キューへ投入する。要求ごとのresponse_eventを待ち、Event解除後は同じLock内でpending_confirmationsから要求を解除する。登録、回答確定、終了時解除、登録解除はconfirmation_lockで排他的に行う。メインスレッドが回答値とresponse_reasonを確定してからresponse_eventを設定する。利用者がTrue/Falseを回答した場合のresponse_reasonはuser_responseとする。Trueは継続、Falseは中止であり、Falseの場合だけWorkerHandle.cancel_reasonが未設定ならcontinuation_declinedを同じLock内で設定する。終了確定時はcancel_reasonが未設定ならapplication_shutdownを設定し、display_started=Falseの未回答要求をFalse（response_reason=application_shutdown）で解除してEventを必ず設定する。display_started=Trueの要求は終了処理が回答を上書きせず、表示中ダイアログの回答または表示例外によってGUI側が解除する。ダイアログ例外・表示不能によるFalseはresponse_reason=confirmation_unavailableとし、cancel_reasonが未設定なら同値を設定する。response_reasonは回答経路、cancel_reasonは取得処理を中止させた原因であり、意味を混同しない。遅延したダイアログ応答はanswered=Trueなら破棄する。True回答確定後に終了が始まった場合もcancel_reasonが未設定ならapplication_shutdownを設定してcancel_eventで停止する。cancel_reasonは最初に確定した原因を保持し、後から上書きしない。確認・通知・終了確認のモーダルダイアログは再入防止フラグとFIFO保留列により直列化する。

## 8. APIクライアント契約
youtube_api_client.pyはtkinterおよびtk_notificationsに依存しない。APIエラーのログとresult_data内のエラー情報を維持し、利用者向け通知はワーカーがnotification要求として登録する。サービス構築失敗時はget_youtube_service()の任意error_callbackで秘匿化した例外概要を取得し、既存のAPIキー確認案内とともに通知へ含める。
fetch_all_comments()の返却タプルは(result_data, fetched_count, total_expected)を維持する。既存fetch_statusの意味を維持し、キャンセルはfetch_status="cancelled"を使用する。APIクライアントは確認応答Falseの発生理由を単独で決めず、WorkerHandleにも依存しない。ワーカータスクがAPI処理終了後にWorkerHandle.cancel_reasonをconfirmation_lockで読み、result_data["cancel_reason"]へ反映する。
- continuation_declined：利用者が確認ダイアログでFalseを回答。
- application_shutdown：アプリ終了に伴う協調的キャンセル。
- confirmation_unavailable：確認ダイアログの例外・表示不能による中止。

response_reasonはuser_response、application_shutdown、confirmation_unavailableを使用する。利用者がTrue/Falseを回答した場合はuser_responseであり、Falseの場合に限ってcancel_reason=continuation_declinedを設定する。
cancel_reasonは補足情報であり、既存のfetch_statusや返却タプルを置き換えない。キャンセル以外の結果ではcancel_reasonキーを追加しない。既存のキーなしデータも有効な入力として扱う。

## 9. 取得タスクの結果契約
_scrape_comments_task()はGUI所有状態を変更せず、結果を戻り値として返す。取得結果は少なくとも次を含む構造化データとする。
- fetch_result：APIクライアントのresult_data
- fetched_count：取得件数
- total_expected：予想総件数
- saved_files：保存を試みたファイルごとの結果一覧
- cancel_reason：該当する場合のキャンセル理由

saved_filesの各要素はkind、path、successを持ち、失敗時はerror等の補足を持つ。kindはvideo_info、channel_info、comments、repliesのいずれかに固定し、pathは保存先の完全なパス、successは実際の保存成否を表す。保存結果を返却構造に集約し、GUI属性last_saved_*_file_path等はmain.pyがsuccess=Trueかつ実際に保存された結果からのみ更新する。失敗・未試行ファイルを保存済みとして扱わず、少なくとも1件の有効な保存済みファイルがある場合は対応するファイルを開くGUI操作を利用可能にする。resultはこの取得タスク結果を保持する。未処理例外はWorkerHandle.exceptionに保持する。

保存結果の途中経過はWorkerHandle.partial_result["saved_files"]へ保持する。各ファイルの保存試行が確定した直後、次のファイルの試行前に結果を追加する。個別ファイルの保存例外はファイル単位の失敗として記録し、安全に続行できる場合は後続ファイルを処理する。各保存結果レコードのkindはvideo_info、channel_info、comments、repliesのいずれかとし、pathは完全パス、successは保存処理の実成否とする。保存処理全体の予期しない例外でタスクが中断しても、すでにpartial_resultへ記録された結果は保持する。正常終了時のresult.saved_filesはpartial_result["saved_files"]と一致させる。異常終了時はdone_event後にmain.pyがexceptionとpartial_resultを別々に回収し、確定済みの部分結果を失わない。未試行ファイルの結果を推測して追加しない。

## 10. 終了判断・保存開始の同期契約
終了確認ダイアログを表示する前にmain.pyはshutdown_lock内でshutdown_pending=Trueとし、shutdown_decision_eventを未設定にする。ワーカーは保存開始直前に同じLockを取得する。
- pending=Trueならロックを解放してshutdown_decision_eventを待つ。Lockを保持したままEvent待機してはならない。
- pending=Falseかつ通常保存が必要なら、同じLock内でsave_started=Trueとして保存開始を確定する。WorkerHandle.begin_shutdown_decision()はdone_eventとsave_startedを同じLock内で確認し、ワーカーラッパーも同じLock内でdone_eventを確定する。resolve_shutdown_decision(save_policy, cancel=True)は同じLock内で自然終了との競合を調停し、未終了ならsave_policyを確定する。終了確定時はconfirmation_lockでcancel_reason・未回答確認要求・cancel_eventを確定してからshutdown_pending=Falseとshutdown_decision_event設定を行い、保存待機ワーカーを起こす。すでに終了済みならFalseを返して終了選択を適用しない。キャンセル選択ではcancel=Falseとしてcancel_eventを設定せずに判断バリアを解放する。begin_save()はpending中にLockを解放してEvent待機する。
- 選択確定後、main.pyはsave_policyを設定し、pending=FalseにしてEventを設定する。キャンセル選択ではcancel_eventを設定しない。はい／いいえではconfirmation_lockでcancel_reasonが未設定ならapplication_shutdownを確定し、display_started=Falseの未回答確認要求をFalse（response_reason=application_shutdown）で解除してからcancel_eventを設定する。display_started=Trueの要求はダイアログ応答または表示例外でGUI側が解除し、終了処理は応答を上書きしない。
- save_policy=save_partialなら取得済みデータの保存を許可する。
- save_policy=skip_additional_saveならまだ開始していない保存を開始しない。
- 保存開始済みの場合は選択で強制中断しない。

終了要求と保存開始は同じLockで調停する。どちらが先に確定したかにより一意に動作し、終了確認中にワーカーが無断で保存へ進む競合を防ぐ。キャンセル選択後は通常の保存方針へ復帰する。

## 11. キャンセル境界
fetch_all_comments()のcancel_eventは省略可能とし、省略時は既存呼び出し元との互換動作を維持する。APIリクエスト開始前にcancel_eventを確認する。execute()実行中は強制中断しない。レスポンスが返った場合はそのレスポンスに含まれるデータを処理・保持してからキャンセルを確認し、後続API要求へ進まない。親コメント・返信ページ処理、ページ間待機、保存開始前にも確認する。ページ間待機はcancel_event.wait(0.1)を使用する。API通信に新規タイムアウトは設定しない。

## 12. 状態遷移
標準状態はrunning、confirming、shutdown_pending、stopping、complete、closedとする。
- running -> confirming -> running：継続確認への回答が確定した。
- running -> shutdown_pending：終了確認を開始した。継続確認ダイアログ表示中に終了要求が来た場合は、そのダイアログが閉じてから終了確認を開始する。shutdown_pending中の通知・確認要求はFIFOへ退避する。
- shutdown_pending -> running/confirming：終了キャンセル。元の通常処理へ戻り、cancel_eventを設定しない。
- shutdown_pending -> stopping：はい／いいえの終了方針を確定し、cancel_eventを設定した。
- stopping -> complete：ワーカー終了、結果回収、GUI後処理が完了した。
- complete -> closed：終了時通知を報告し、WorkerHandleを解放してrootを破棄した。

ワーカー自然終了が終了ダイアログ表示中に発生した場合は、選択を遅れて適用せず、通常の完了回収へ移る。二重の完了処理・追加保存を行わない。

## 13. 終了時の通知・破棄順序
終了時は、ワーカー終了検知、未処理要求回収、result/exception/partial_result（保存結果を含む）回収、GUI後処理、通知サマリー表示、WorkerHandle解放、root破棄の順とする。終了待機中もGUIイベントループを動作させる。root破棄後にafter()を登録しない。

## 14. 互換性・旧方式の撤去
Python 3.8.10を維持し、新規外部依存を追加しない。queue/threading等の標準ライブラリを使用する。
旧run_task_in_thread呼び出し、confirm_continuation_gui()、BooleanVar/wait_variable方式、ワーカーからのroot.after()、Tk通知呼び出しは、全呼び出し箇所の移行と検索確認が完了したStageで撤去する。Stage 2では既存のconfirm_continuation_gui()／BooleanVar／after()／wait_variable()経路とyoutube_api_client.py内の既存tk_notifications呼び出しを明示的な移行例外として残し、Stage 3で撤去する。移行期間中は互換経路を残してもよいが、新旧方式を同じ処理経路で混在させない。

### 15.1 テスト環境の確認結果（2026-11-21）
既存テストを対象に、Python 3.8.10環境でテスト探索・実行方法を確認した。
- このリポジトリの現在のディレクトリ構成では、unittest discoverによるサブディレクトリの再帰探索に、テストファイルを含む各階層のパッケージ化（空の__init__.py）が必要だった。
- module/以下の親ディレクトリおよびテスト配置先の各ディレクトリに合計13個の空の__init__.pyを追加した検証環境では、リポジトリルートからテストを一括探索できた。
- python -m unittest discover -v：50テストを検出し、全件成功。
- python -m pytest -v（pytest 8.3.5）：同じ50テストを検出し、全件成功。
- この結果は、検証時点で存在した既存テスト50件の探索・実行結果であり、Issue #3のStage 1〜4で定義した新規テストが実装済み、または検証済みであることを意味しない。

テストランナーは、Python標準ライブラリで追加依存のないunittestを基本候補とし、pytestを補助的に利用する案をIssue #20で確定する。Tkinterのイベントループを伴う統合テストは、ヘッドレス環境で実行できる単体テストと区別し、実デスクトップ環境での検証方法・実行条件をIssue #20で整備する。テストコードの配置・命名・実行手順もIssue #20で最終決定する。

## 17. Stage 3実装反映後の実インターフェース記録（2026-11-22）

Stage 3実装で確定した実コード上の契約を記録する。

- WorkerHandle.request_confirmation(message) は要求を pending_confirmations に登録し、同じ confirmation_lock 保護区間でGUI要求キューへ投入してから、要求固有の response_event を待つ。待機終了時はfinally経路で登録を解除する。
- 確認応答の response_reason は user_response（True/Falseの利用者回答）、application_shutdown（終了による未回答解除）、confirmation_unavailable（表示不能・表示例外）を表す。cancel_reason は取得処理を止めた原因を表し、最初に確定した値を保持する。
- youtube_api_client.fetch_all_comments() は従来どおり3要素タプルを返す。通知分類は result_data["notifications"] の各レコード（stage、kind、title、message）で返し、APIクライアント自身はTkinter通知を行わない。
- 確認・通知モーダルはGUI側で直列化し、表示中の再入要求をFIFO保留列に置く。終了処理開始後は保留中の古い確認要求を新たに表示しない。

上記はStage 3の実装反映記録であり、Issue #20による新規テスト実装・実行の完了を示すものではない。実装とテストの差異が見つかった場合は、Issue #20でテスト結果を記録し、必要に応じて本書とStage設計・テスト仕様を同期修正する。
