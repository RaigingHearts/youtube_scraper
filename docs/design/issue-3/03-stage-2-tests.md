# Issue #3：Stage 2 テスト仕様 — 進捗表示・通知・取得結果のGUI集約

## 1. 目的・対象

Stage 2で、実際の取得処理からの進捗表示・通知・取得結果の受け渡しをGUI要求基盤へ移行し、ワーカー側の`_scrape_comments_task()`がTkinterを直接操作せず、GUI所有状態を直接変更しない構造になったことを検証する。`main.py`はメインスレッド上でGUIを更新する責務を持つため、そのGUI操作自体は撤去対象ではない。

対応する設計書は `03-stage-2-design.md`。共通契約は `09-cross-stage-interface.md`、共通テスト観点は `11-common-test-spec.md` に従う。本書は期待動作と受け入れ条件を定義するもので、テストコードの実装はIssue #20で行う。

## 2. Stage 2の適用範囲と移行例外

Stage 2で移行する対象：
- `main.py` および `_scrape_comments_task()` からの進捗更新。
- `_scrape_comments_task()` からの利用者向け通知要求。`main.py`はメインスレッドで通知を表示する。
- 取得件数、総件数、保存先、ファイル単位の保存結果等のGUI所有状態への反映。
- 取得タスクの戻り値と `WorkerHandle.result` を通じた結果回収。

Stage 2の実装途中では、`youtube_api_client.py` 内部の既存 `tk_notifications` 呼び出しを一時的な移行例外として許容していた。これはStage 3で撤去済みであり、Issue #20で全Stage統合後に実行する最終テストでは、この旧経路の存在を期待・許容しない。最終契約はStage 3テスト仕様 §3・§4に従い、APIクライアントが通知情報を返し、アプリケーション層がGUI要求キュー経由で通知することである。

## 3. 進捗集約・表示

### 3.1 WorkerHandleとの接続
- `_scrape_comments_task()` が進捗を報告するとき、ウィジェットやTk変数を参照せず `WorkerHandle.publish_progress()` を使用する。
- 進捗情報には画面表示に必要な値を含め、Tkinterオブジェクトを含めない。
- 連続した複数更新は最新値へ集約され、マーカー要求が不必要に増殖しない。
- メインスレッドがマーカーを処理すると、`take_latest_progress()` から最新値を取得して表示する。
- 進捗更新がマーカー処理と競合しても、最新状態が取りこぼされない。
- 進捗値が存在しないマーカーは安全な空状態として処理する。

### 3.2 表示内容とスレッド境界
- 進捗ラベル、プログレスバーの値・最大値・状態はメインスレッドだけが更新する。
- ワーカー側の`_scrape_comments_task()`から `root.after()`、ウィジェットの `config()`、Tk変数のget/setを呼び出さない。`main.py`によるメインスレッド上のGUI更新は許容する。
- 進捗表示の更新例外をログへ記録し、後続GUI要求とポーリングを継続する。
- 進捗の完了・不明値・キャンセル等の表示が既存仕様と一致する。

## 4. 通知要求

- `_scrape_comments_task()` が利用者向け通知を必要とする場合、GUI要求キューへnotification要求を登録する。
- 要求payloadは `kind`（info／warning／error）、`title`、`message` を保持し、Tkinterオブジェクトを含めない。
- 通知はメインスレッド上で `tk_notifications` 経由に表示される。
- 複数通知はFIFO順で1件ずつ表示され、モーダルダイアログを重ねない。
- 1件の通知表示で例外が発生しても、後続通知、ポーリング、ワーカー完了回収が継続する。
- Stage 2途中ではAPIクライアント内部の既存通知を一時維持していたが、これは移行履歴であり最終テストの期待動作ではない。最終状態ではAPIクライアントは通知情報を返し、アプリケーション層がGUI要求キュー経由で表示する（Stage 3テスト仕様 §3・§4）。
- `_scrape_comments_task()`は`fetch_result["errors"]`をそのままnotification要求へ変換せず、APIクライアントが通知する同一事象を再通知しない。
- タスク側のnotification要求は、保存結果やタスク固有の状態など、APIクライアントの既存通知とは別の事象に限定する。
- main.pyがワーカー例外を通知する場合も、同一事象についてAPIクライアントの既存通知と重複させない。
- API通知とタスク通知が同一事象を指す可能性がある場合は、APIクライアント側の既存通知を優先し、タスク側の重複要求を作らない。
- 通知の発生元と事象をテストで識別し、必要な通知が欠落・重複・順序変更されないことを確認する。

## 5. _scrape_comments_task() のGUI非依存性

静的検索とモックを併用して次を検証する。

- `tkinter` ウィジェット、Tk変数、rootを直接参照しない。
- `master.after()` やその他のTkイベントスケジューリングを直接呼び出さない。Stage 2途中では既存の継続確認`confirm_continuation_gui()`／BooleanVar／`after()`／`wait_variable()`経路を一時的に残していたが、Stage 3で撤去済みである。最終テストでは旧経路が残っていないことと、Stage 3仕様に従うEvent方式を検証する。
- `tk_notifications` を直接呼び出さない。`youtube_api_client.py`内部の既存通知呼び出しもStage 3で撤去済みであり、最終テストではAPIクライアントがTk通知を直接呼び出さないことを検証する。
- GUI所有属性（例：取得件数ラベル用属性、保存先パス属性、プログレスバー最大値等）を直接更新しない。`main.py`がメインスレッド上でこれらを更新することは本Stageの目的に含む。
- 必要な進捗・通知はWorkerHandle／GUI要求キューへ渡す。
- 画面更新に必要な取得結果は戻り値として返す。

Stage 2の主な検証対象は `main.py` と `_scrape_comments_task()` の進捗・通知・結果受け渡しである。Stage 2途中の移行例外（APIクライアント内の旧通知経路、旧継続確認GUI経路）は最終状態に残してはならず、その撤去と最終契約はStage 3テスト仕様で検証する。

## 6. 取得結果・保存結果の受け渡し

### 6.1 正常終了
- `_scrape_comments_task()` の戻り値が `WorkerHandle.result` に保持される。
- 戻り値は共通インターフェース仕様の構造を満たし、少なくとも `fetch_result`、`fetched_count`、`total_expected`、`saved_files` を含む。
- 保存ファイルごとの結果は `kind`、`path`、`success` を持ち、必要に応じて失敗理由を含む。`kind`は`video_info`、`channel_info`、`comments`、`replies`のいずれかとし、`path`は完全パス、`success`は実際の保存成否を表す。
- メインスレッドがresultを回収し、取得件数・総件数・保存先等のGUI所有状態を更新する。
- GUI属性の更新はワーカー終了後のメインスレッド上で行う。

### 6.2 保存部分失敗・例外
- 個別ファイルの保存失敗はファイル単位の結果として返され、安全に続行可能な後続保存を妨げない。
- 保存途中で予期しない例外が発生した場合、既に確定した `partial_result["saved_files"]` が保持される。
- 正常終了時の `result.saved_files` と `partial_result["saved_files"]` が一致する。
- ワーカー例外終了時、main.pyはexceptionとpartial_resultを別々に回収し、確定済みの保存結果を失わない。
- 未試行ファイルの結果を推測して追加しない。
- 保存結果の成功・失敗に応じたGUI表示が実際の保存結果と一致する。`last_saved_*_file_path`等は`success=True`かつ実際に保存されたレコードからのみ更新し、失敗・未試行ファイルを保存済みとして扱わない。1件以上の有効な保存済みファイルがある場合、該当ファイルを開くGUI操作を利用可能にする。

### 6.3 既存動作の維持
- 既存の取得状態、取得件数、総件数、保存先パス、保存形式、ファイル名、保存順序を不必要に変更しない。
- 既存のAPI結果構造・fetch_statusの意味を維持する。
- 既存データやキー欠落を含む旧形式の入力を壊さない。

## 7. ワーカー完了処理とGUI復旧

- 正常終了時にresultを回収してGUI状態へ反映した後、取得ボタン等を復旧する。
- 例外終了時はexceptionとpartial_resultを回収し、確定済みの保存結果をGUI状態へ反映したうえで適切な通知とGUI状態復旧を行う。
- 通知表示が失敗してもGUI状態復旧を妨げない。
- 通常稼働中の完了時に未処理の進捗・通知要求を失わず、規定の順序で処理する。終了処理中の通知退避・サマリー表示・個別通知抑制はStage 4の検証対象とする。
- WorkerHandleを早期解放せず、必要な結果回収とGUI後処理の完了後に解放する。
- 完了後に次の取得処理を開始できる。

## 8. テストダブルと検証方法

- YouTube APIクライアントおよびネットワーク通信はモック化し、実APIへ接続しない。
- ファイル保存は一時ディレクトリまたは保存関数モックを使用する。
- GUI通知・進捗表示のモックは呼び出しスレッドIDを記録し、メインスレッドでの実行を検証する。
- WorkerHandleの進捗更新とGUI要求キューの連携を単体テストする。
- main.pyとTkイベントループの連携はGUI統合テストとして分離する。
- 静的検索は直接GUIアクセスの残存候補を発見するために使い、モックによる実行スレッド検証と組み合わせる。
- テストは正常系、APIエラー、通知例外、保存成功、保存部分失敗、保存全体例外、ワーカー例外、進捗更新競合を含む。

## 9. Stage 2の受け入れ条件

次のすべてを満たしたときStage 2を完了とする。

1. `_scrape_comments_task()` の進捗・通知がWorkerHandle／GUI要求キュー経由になっている。
2. ワーカー側の`_scrape_comments_task()`から直接Tkinter操作・GUI所有状態更新が撤去され、`main.py`によるGUI更新はメインスレッド上で行われる。
3. 進捗・通知・結果反映がメインスレッド上で行われる。
4. 取得結果と保存結果が規定の構造で受け渡され、GUI表示が実際の結果と一致する。
5. 部分保存結果・例外時の後始末が保持される。
6. Stage 2途中で一時許容したAPIクライアント内の旧通知経路と旧継続確認GUI経路はStage 3で撤去済みであることを、Stage 3テスト仕様と合わせて最終統合状態で確認する。

### 9.1 Stage 2実装完了とテスト検証完了の区別
Stage 2のアプリケーション実装完了と、Issue #20におけるStage 2新規テスト検証完了は別の状態として管理する。既存回帰テストの成功や静的整合性確認だけを、新規機能テストの検証完了と読み替えない。

Stage 1テスト作業ブランチの `test_main.py` には、`test_finish_worker_restores_widgets_and_saved_file_paths`、`test_finish_worker_keeps_json_button_disabled_without_saved_files`、`test_real_event_loop_processes_worker_requests_before_releasing_handle` に、Stage 2の進捗・通知の実処理接続または取得結果・保存結果のGUI反映を確認する補助的なクロスStage回帰アサーションが含まれる。最後の実イベントループ統合テストはStage 1のキュー処理・完了順序も検証する。これらはStage 2専用テスト群の件数には算入しない。

Issue #20でStage 2専用テストを実装・実行し、仕様との横断確認を行った結果は次節に記録する。Stage 2のテスト検証完了は、専用テストの実行成功だけでなく、設計・共通インターフェース・実装・テストの整合確認と作業記録をもって判断する。Stage 1～4を横断する統合検証および実デスクトップ環境での受け入れ確認は、別途の完了条件として管理する。

## 11. 通知重複とStage 4との境界
- 最終実装ではAPIクライアントはAPIサービス構築・API取得に起因する通知情報を返し、アプリケーション層がGUI要求キュー経由で表示する。APIクライアント自身はTk通知を表示しない（Stage 3テスト仕様 §3・§4）。
- _scrape_comments_task()はfetch_result["errors"]をそのまま通知せず、APIクライアントが通知した同一事象を重複表示しない。タスク側の通知は保存結果やタスク固有の状態など、別の事象に限定する。
- main.pyによるワーカー例外通知も、APIクライアントが既に通知した同一事象を重複表示しない。
- APIクライアントが返す通知情報とタスク固有の通知要求の責務を識別し、アプリケーション層で同一事象に対する二重表示がないことを検証する。
- Stage 2では通常稼働中のFIFO通知表示と通知表示例外後の継続を検証する。
- 終了処理開始後の個別通知抑制、通知の退避、終了時サマリーへの集約、サマリー表示後のroot破棄順序はStage 4の検証対象とし、Stage 2の受け入れ条件に含めない。
