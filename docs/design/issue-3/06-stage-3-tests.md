# Issue #3：Stage 3 テスト仕様 — 継続確認のEvent方式への移行とAPIクライアントのGUI依存解消

## 1. Event確認
確認要求のpending_confirmationsへの登録とキュー投入、ワーカー待機、Event解除後の登録解除、True継続、False中止、要求ごとのEvent独立性、回答一度限り、ダイアログ例外時のFalse解除、終了処理による未回答解除、確定済み応答の不変性を確認する。要求登録中・回答確定中・終了解除中の競合で登録漏れ、二重解除、pending_confirmationsの残留がないことを確認する。回答確定と終了解除が競合してもresponse_eventが必ず設定され、responseとresponse_reasonが後から上書きされないことを検証する。利用者のTrue回答が先に確定した後で終了要求が発生した場合は、response=Trueとresponse_reason=user_responseが維持され、cancel_reason=application_shutdownが設定されてワーカーが停止することも検証する。利用者がTrue/Falseのいずれかを回答した場合はresponse_reason=user_responseとなることを確認する。False回答時のみcancel_reason=continuation_declinedを設定する。終了解除が先に確定した場合はresponse_reason=application_shutdownかつcancel_reason=application_shutdown、ダイアログ例外・表示不能によるFalseはresponse_reason=confirmation_unavailableかつcancel_reason=confirmation_unavailableとなることを確認する。response_reasonとcancel_reasonを混同しない。

## 2. ダイアログ直列化
確認・通知・終了確認のモーダルダイアログが同時に表示されないことを確認する。モーダル表示中にTkinterのネストしたイベントループからポーリングが再入しても、次のダイアログが開かず、notification/confirmation要求がFIFOで保留されることを確認する。ダイアログ表示例外後に表示中フラグが解除され、後続要求が処理されることを確認する。確認要求のdisplay_started設定と終了処理を競合させ、Lock内で表示開始が先に確定した要求は終了処理が回答を上書きせず、表示開始前の要求はapplication_shutdownで解除されることを確認する。確認表示中に終了要求が発生した場合、確認応答を一度だけ確定した後に終了処理へ移ること、終了開始後に新しい確認ダイアログを表示しないことを確認する。ワーカー例外通知がGUI要求キュー経由で一度だけ表示され、保留中のモーダル要求が残る間はワーカー完了処理が確定しないことも確認する。

## 3. APIクライアント独立性
youtube_api_client.pyがtkinterとtk_notificationsをimportせず、API処理からダイアログを表示しないことを確認する。エラー情報・ログが保持され、呼び出し元が通知内容を構成できることを確認する。

## 4. APIエラー
サービス生成、動画情報、チャンネル情報、コメントスレッド、返信ページの各エラーをモック化する。従来通知対象のサービス構築失敗・動画情報APIエラー・チャンネル情報APIエラー・返信ページ失敗・コメントスレッド失敗はerror、videoNotFoundはwarning、commentsDisabledは専用warningとして一度だけ通知されることを確認する。サービス構築失敗通知にはAPIキー確認案内と秘匿化された例外概要が含まれることを確認する。動画情報なし・チャンネル情報なし等、従来ログのみだった事象は通知されないことを確認する。既存fetch_status、result_data、取得件数、返却タプル構造を維持する。同一エラーの二重通知が発生しないことを確認する。

## 5. キャンセル理由
利用者が明示的にFalseを選んだ場合はfetch_status="cancelled"かつresult_data["cancel_reason"]="continuation_declined"となること、アプリ終了解除ではresult_data["cancel_reason"]="application_shutdown"となることを確認する。ダイアログ例外・表示不能ではconfirmation_unavailableとなることを確認する。WorkerHandle.cancel_reasonがワーカータスクからresult_dataへ伝達され、APIクライアントがWorkerHandleに依存しないことを確認する。キャンセル以外の結果ではcancel_reasonキーが存在しないことを確認する。既存のcancel_reasonキーなしデータも従来どおり読み取れることを確認する。

## 6. 継続確認統合
Trueで後続取得、Falseで中止、部分取得データの保持、上限到達が複数回発生した場合の動作を確認する。

## 7. スレッド境界・GUI統合
確認ダイアログはメインスレッド、ワーカーはEvent待機、APIクライアントはGUI非操作であることを確認する。モックAPIと実際のTkイベントループを使用する。

## 8. 完了条件
Python 3.8.10環境で、Event確認の正常・異常・競合系とAPIクライアントのGUI非依存性を検証できること。


## 9. 実装反映後のIssue #20引き継ぎ事項（2026-11-22）

Stage 3の実装では、APIクライアントの通知情報は result_data["notifications"] に格納される。各通知レコードは stage、kind、title、message を持つ。既存の fetch_all_comments() の3要素タプルは維持される。

既存の module/utility/youtube_api_client/test_youtube_api_client.py は youtube_api_client.tk_notifications をpatchするテストを含むが、実装モジュールから同属性は削除された。Issue #20では、これらのpatchを撤去し、返却される notifications の内容・種別・件数を検証するテストへ更新する。既存テストの期待値を機械的に置き換えるのではなく、従来通知対象とログのみの事象の区別、重複通知防止、戻り値・取得結果の互換性を確認する。

追加する主な検証対象：
- WorkerHandleの確認要求登録とキュー投入の同期、要求ごとのEvent独立性、Event解除後の登録解除。
- True/False回答、ダイアログ表示例外、アプリ終了による未回答要求解除、および回答確定と終了処理の競合。
- True回答確定後に終了要求が発生した場合、response=True／response_reason=user_responseを維持し、未設定のcancel_reasonにはapplication_shutdownを設定すること。
- モーダルダイアログ表示中のポーリング再入、FIFO保留、表示例外後のフラグ解除、終了後の古い確認要求の抑止。
- APIクライアントのTkinter非依存、通知分類（error／warning）、commentsDisabledの一度限りの通知、従来ログのみだった事象を通知へ昇格させないこと。
- fetch_status、result_data、3要素タプル、取得件数の既存契約とキャンセル理由の伝達。

本書のテスト仕様は期待動作の定義であり、上記テストが実装・実行済みであることを意味しない。テストコードの実装と検証はIssue #20で行う。
